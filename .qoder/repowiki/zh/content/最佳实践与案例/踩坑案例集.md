# 踩坑案例集

> 全部来自本仓库真实事故，按根因分类。**每类坑的共性是：静默失败。** 系统不报错，但结果已经错了。
> 详细 QMT 条目见 `全局复利与踩坑日志.md` 与 `broker/QMT委托买卖防坑指南.md`。

---

## 一、数据口径类

### 1.1 单位坑：moneyflow 的 amount 是万元

Tushare `moneyflow` 接口 `amount` 字段单位是**万元**，历史 parquet 同样以万元存储。初版 `refresh_tushare_moneyflow.py` 误 ÷1e4，导致新刷数据偏小 1 万倍，已回滚重刷。

- 判据：**量级突变 1e4 倍即为单位 bug 信号**。
- 同类：`circ_mv` 单位也是万元（30 亿 = 300000）。
- 纪律：改任何资金流/财务/行情同步脚本，**先抽活跃大盘股（如 600519.SH）核对原始字段单位与量级**，再决定是否换算。

### 1.2 口径坑：F2 主力资金用了隔日数据

TDX 返回 503 后降级 iFind，取到**前一日**口径，用 8/28 的 +5.26 亿打 F2=10 分；实际东财口径 8/28 为 -2.79 亿、8/31 当日 -1.25 亿，**方向全反**（真实 F2=1，总分 86→68）。

- 修复：评分卡坚持**当日口径**；`_valid_main_inflow` 做时效校验，**非当日即按缺失计 5 分**；9:25 增加双源对拍 crosscheck，不一致打 `[交叉验证]` 预警。
- 教训：降级不能只换源，还要检查**口径（统计日期）是否仍然成立**。

### 1.3 列名坑：vol_ratio_5_20 全量 NaN

增量库列名为 `volume`，而 `build_g2_daily.RAW_COLS` 要 `vol`，静默跳过 → 快照中该因子 **100% NaN**，缺失率修复后降至 0.21%。

- 教训：**缺失率必须做监控**。100% NaN 的因子照样能"跑通"回测，只是该维度完全失效。

### 1.4 前视偏差

财务数据必须走 `AstockFinanceReader`（按 `ann_date` / `f_ann_date` 对齐）。直接按报告期 merge 是最高频的未来函数来源。同理，股票池要用 `universe_by_date`（PIT 池）而非固定池。

## 二、回测方法论类

### 2.1 幸存者偏差：Project_01 表面收益 vs 真实超额

修复幸存者偏差后，Project_01 超额从表面收益降到仅 BP 因子 **+6.1%/年**，且 **2024 年后转负** → 判定不建议实盘。

### 2.2 回测非确定性：risk_state 污染

`risk_state` 跨 run 污染导致年化虚高（18% → 修复后 35.7% 是另一口径，污染版本更高）。**回测必须可复现**：同输入同输出，`hashing.py` 的 `universe_hash` / `data_hash` / `config_hash` 就是为此存在。

### 2.3 风控频率错觉（最贵的一个坑）

Project_10 的「18.0% 年化」是**双月 open 状态机 + 双月才查风控**的口径；改成**真实每日风控**口径后约 **7.5%**。拆解：风控频率贡献 -8.3pp，结算频率仅 -2.2pp。

- 教训：**任何回测结论都必须标注风控频率与结算频率**，否则数字不可比。

### 2.4 掩码缺失：约 18% 收益是涨跌停虚增

不做涨跌停/停牌掩码前置（MASK=1），回测收益中约 18% 是拿不到的。**掩码前置应固化为全框架标准地基**。

### 2.5 容量幻觉

Project_10 实测容量上限约 1000–2000 万，**5000 万时收益减半**。小资金回测的好成绩不能直接外推。

### 2.6 样本量幻觉

前向验证按「笔数」计数会高估。同日选出的多只票高度同向（G2 实测组内相关 ICC ρ≈0.68），有效样本 `n_eff = n / (1 + (m-1)ρ)`。**「N>30 笔」在 m=2、ρ≈0.68 时仅相当于约 18 个独立观测。**

### 2.7 vol_target 在 ATR 策略上退化为永久低仓

ATR 自身波动 ~18.5% > 目标 15%，稳态波动率缩放会**匀速砍仓**，削掉复利主力年。这是 `risk/` 只做尾部守卫（CrashGuard）而不做稳态缩放的直接原因。

### 2.8 基准口径错误伪造出「强显著」（2026-09-05）

审计「60线归位战法」时，用「每日调仓的池内等权净值 cumprod」作为个股事件基准，得出**小市值域 +5.30%、t=5.66** 的强显著结论；改用**买入并持有基准**后坍塌为 **+0.34%、t=0.37**——所谓 alpha 基本是基准造的假。

- **根因**：分层池（尤其市值分位池）成员每日变动，上涨个股升出池外，基准被迫截断其后续收益（成分漂移 / 再平衡偏差），池子越小偏差越大。
- **三条纪律**（已固化进 `factors/factor_audit.py`）：
  1. **个股怎么持有，基准就怎么持有**；
  2. **分层结论必须在该层内部做随机对照**——先看该层随机抽签能拿多少，若随机值本身远离 0，说明基准有偏，t 值再大也无意义；
  3. **止损必须同步施加于随机对照组**，否则只是截断左尾，制造"改善"假象。
- 判定门槛：真实信号须位于随机分布 **95 百分位**以上。

## 三、QMT 实盘类

### 3.1 代码格式：`600522.SH` 被翻转成 `SH.600522`

`_to_qmt_code` 错误翻转代码 → QMT 主日志 `orderCode:600522SH 不合法!`，**passorder 返回 0 但委托从未进通道**（界面无记录、反查无单）。对照：ATR(`601985.SH`)、V2(`600000.SH`) 数字在前，实盘成交正常。

- 验证方法：部署后核对 QMT 主日志是否出现 `CTradeClient::order`。

### 3.2 撤单：passorder 没有"撤单"这个 opType

`passorder(24, ...)` 里的 **24 是股票卖出**，不是撤单。用它假装撤单会被当卖出拒（`下单数量/金额/比例为0`），用户亲见界面"显示卖出不是撤单"。

- **正确姿势：`cancel(orderId, acct, 'stock', C)`**，配合 `can_cancel_order(...)` 预检，`orderId = m_strOrderSysID`（柜台合同号）。
- `cancel()` 返回 True 仅表示**指令送达**，需轮询确认终态。

### 3.3 订单字段的真相（实测值，勿信推测）

| 用途 | 字段 |
| --- | --- |
| 真实 QMT 平台委托号 | `m_nOrderID`（优先） |
| 柜台合同号（撤单用） | `m_strOrderSysID` |
| 真实成交量 | `m_nVolumeTraded`（**不是** `m_nDealVolume`，后者读 0） |
| 方向判断 | `m_strOptName`（含中文「买入」/「卖出」），勿用 `m_nDirection` |
| 状态码 | **55（部成）是活跃态，不是终态**；终态排除集 53/54/57 |

### 3.4 参数类型：passorder 第 6 参要 int

`[CANCEL-ERR] order_id=2882: Python argument types` —— 传 str 会**静默失败**。

### 3.5 策略崩溃：心跳写文件的 PermissionError

handlebar 的 `not in_session` 分支里 `_write_heartbeat` 没包 try/except；`os.replace` 原子改名撞上外部监控的文件锁 → WinError 5 未捕获 → **策略 Python 崩溃，下午 handlebar 全部停触发**。

- 修复：`_atomic_write_json` 遇 OSError 重试 5 次 + 心跳调用处包 try/except。
- 教训：**QMT 策略里任何文件 IO 都必须容错**，一次未捕获异常就是半天停摆。

### 3.6 孤儿持仓

账户有票、账本没记录 → 止损/止盈**永不触发**。卖出风控评估前必须同步账户全量持仓纳管；孤儿只纳管不误杀。

### 3.7 模拟端限制

- `get_trade_detail_data` 只保留当日 deal/order，**隔日查不到** → 每日导出 CSV 到 `D:/QMT_POOL/` 是刚需；
- 分钟线历史只有近 1 年；
- 内置 Python 不保证有第三方包（如 pyyaml），import 必须 try/except fallback；无 pyarrow，不能读 parquet。

### 3.8 时间源

策略时间必须用 `C.get_current_time()`，不能用 `datetime.now()`（CMOS 时钟可能错乱）。相对计时用 `time.time()`。收盘 15:00 后 handlebar 不再触发，>15:00 的任务永不执行。

## 四、工程管道类

### 4.1 生成侧与核算侧不同源 = 死局（反复出现三次）

典型案例（T-20260904-009）：`paper_forward.py --backfill` 只依赖**人工周更**的 `Updatedata/`（常滞后 7 天以上），而选股侧用**自动日更**的增量库 → 候选每天照常产生、收益一笔也算不出，连续 4 天「回填 0 笔」仍 **exit 0 静默**，有效样本实为 N=0 却被记成「9 个交易日」。

- 判据（应作每日硬断言）：**`候选日期最大值 > 收益数据源最新日` 即为死局。**
- 修复：主库 + 增量合并（增量优先），数据源停更 → **exit 2**；调度脚本捕获并转发退出码（fail-loud）。

> **规律：任何「生成侧与核算侧不同源」的管道，必然出现「能出信号、无法验证」的死局。** 这是本项目同类问题的第三例，前两例分别是 8/28 数据更新走旧路径与 8/31 口径滞后。

### 4.2 零产出必须 fail-loud

回填 / 统计类任务输出 0 笔，**不得以 exit 0 报 OK**。要么显式告警，要么非零退出码。

### 4.3 定时任务环境与交互环境不同

项目级 `.mcp.json` 未登记某个 MCP 时，定时任务加载不到 → 调用"不可达"（悟道连续两天挂掉即由此）。

- 另：早先文档推断的悟道 `/api/openclaw` 路径**实测 404 不存在**，真实端点是 `https://stock.quicktiny.cn/api/mcp`。
- 教训：**远程数据源一律写 Python 直连客户端**，不要依赖客户端插件层；文档里的端点必须实测过再写。

### 4.4 未实测的推断值不要写进文档

`passorder opType=24`、悟道 `/api/openclaw`、`m_nDealVolume` 都是"看起来对但没实测"的推断，三者全部翻车。

### 4.5 PS5.1 `ErrorActionPreference="Stop"` 遇 Native stderr 静默终止（2026-09-10）

包装脚本 `nightly_check_task.ps1` 首版设 `$ErrorActionPreference = "Stop"`——PowerShell 5.1 下 **Native 命令（python）stderr 经重定向会触发 ErrorRecord**，Stop 策略直接**静默终止**脚本：日志只有开始行、报告未更新、无任何错误输出。修复：去掉 Stop（与 `run_scheduled.ps1` 同口径）+ Python 加 `-u` 无缓冲防块缓冲丢日志。教训：**PS5.1 包装脚本不要对含 Native stderr 的链路设 Stop**。

### 4.6 编辑工具改写丢 UTF-8 BOM → 中文 .ps1 解析崩溃（T-20260903-015）

Windows PowerShell 5.1 对无 BOM 文件按 ANSI/GBK 解码 → 中文变乱码 → 字符串引号被吞 → 级联「意外的标记」解析错误（`run_scheduled.ps1` 在 powershell.exe 下崩溃）。**每次编辑含中文的 .ps1 后必须校验 BOM 仍在**（`Write`/编辑工具改写会丢 BOM；补法：`[System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding $true))`）。

### 4.7 双调度器对同一产物文件双注册（T-20260910-008）

QuantLab（schtasks）与 TW（TraeWORK 定时任务）各自注册了生成 `positions_cfg_v13_<date>.json` 的 09:00 任务——**同日注册、次日将同时首跑**，撞车恰好发生在首次、归因最难。处置：TW 任务暂停→删除，唯一 owner = QuantLab schtasks。教训：**双端都能碰同一产物文件时，任何一方建调度前必须互查对方已注册的任务清单**；事后取证靠产物文件落盘时间戳（历史时间全在收盘后 → 判定"TW 调度从未生效"）。

## 五、通用防御清单

| 场景 | 防御动作 |
| --- | --- |
| 改数据同步脚本 | 先抽 600519.SH 核对单位与量级 |
| 依赖人工更新的数据 | 加新鲜度硬断言，落后即 fail-loud |
| 批处理产出为 0 | 非零退出码 + 告警 |
| 因子入面板 | 检查缺失率（100% NaN 能"跑通"） |
| 回测结论 | 标注风控频率、结算频率、容量、是否掩码前置 |
| 实盘部署 | 核对 QMT 主日志 `CTradeClient::order` |
| 策略里写文件 | 全部 try/except + 重试 |
| 账本加载 | 校验 `account_id` 戳，不匹配即备份并空仓起步 |
| 调研/选型结论 | 立即落盘（MEMORY.md 或知识库），避免重复调查 |
