# 架构设计

## 数据流

```
飞书用户消息
   │
   ▼
listen.py（常驻进程，WebSocket 长连接，实时）
   │  写 data/feishu_bridge/inbox.jsonl（按 message_id 去重）
   ▼
WorkBuddy 定时任务「飞书消息桥接：处理并回复」（每小时）
   │  bridge.py pending → AI 处理 → bridge.py reply
   ▼
飞书回复（im +messages-reply，成功后标记 processed.json）
```

## 为什么拆两层

WorkBuddy 定时任务最小调度粒度为 1 小时（rrule 仅支持 HOURLY/DAILY/WEEKLY/MONTHLY/YEARLY）。
若只靠定时任务里的 `pull`，两次运行之间到达的消息会永久丢失。
因此拆为「常驻捕获（零丢失）+ 定时处理（有延迟）」。

## 关键机制：Agent 环境变量隔离

`lark-cli` 检测到 Agent 环境变量（`OPENCLAW_CLI` / `HERMES_HOME` / `LARK_CHANNEL`）时，
拒绝读取 `~/.lark-cli/config.json`，报：

```
openclaw context detected but lark-cli is not bound to it
```

`lark-cli config bind` 在本机**三源全不可用**：

| 源 | 结果 |
|---|---|
| `--source openclaw` | 缺 `C:\Users\Administrator\.openclaw\openclaw.json`（不存在） |
| `--source hermes` | `does not match detected Agent environment (openclaw)` |
| `--source lark-channel` | 同上 |

**解法**：调用 lark-cli 时清掉这些变量（`bridge.py::clean_env()`）。
与 P16 `qmt_monitor._env_for_cli()` 同款做法，是本机唯一可用路径。

## 进程与任务

| 组件 | 启动方式 | 幂等机制 |
|---|---|---|
| `listen.py` | 计划任务 `QuantLab_FeishuListen_Boot`（登录）/ `_Guard`（每日 00:00 起每 5 分钟） | pid 文件 `listen.pid`，已在跑则退出 |
| 处理回复 | WorkBuddy 定时任务「飞书消息桥接：处理并回复」（每小时） | `processed.json` 按 message_id 去重 |

两个计划任务均为 `S4U` / `RunLevel=Limited`，
Action = `powershell -NoProfile -ExecutionPolicy Bypass -File start_feishu_listen.ps1`。

## 事件载荷

`lark-cli event consume im.message.receive_v1 --as bot` 输出 NDJSON，
`jq_root_path = "."`，关键字段：`message_id`（幂等键，勿用 `event_id`）、
`chat_id` / `chat_type`(p2p|group) / `content`（已渲染为可读文本）、
`sender_id`（open_id）/ `sender_type`(user|bot) / `create_time`（ms 时间戳）。

`bridge.py::normalize()` 过滤 `sender_type == bot`（避免自问自答死循环）。
