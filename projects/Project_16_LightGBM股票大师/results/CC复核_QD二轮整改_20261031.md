## 3. ❌ 主要问题：午间多行 INIT 修复是死代码

### 3.1 探针（可复现）

我构造了一条真实形态的多行 INIT 日志（首行带 `reqid` 前缀 + `[P16SIG][EXEC] INIT`，次行裸写 `BUILD_TAG=`），走**完整链路** `_scan_log → _summarize_events`：

```
== _scan_log 收到的事件数 = 1
    ('INIT', '', '2026-10-30 08:52:25')
== _summarize_events 结果 ==
   init_tag = ''
== 绕过 _scan_log 直接喂两条事件 => init_tag = '20261030-999999'
```

**结论：走真实链路取不到 TAG；只有绕过 `_scan_log` 才取得到。**

### 3.2 根因

`p16_midday_report.py:151-153`：
```python
em = LINE_RE.search(line)          # LINE_RE = \[P16SIG\]\[EXEC\] ([A-Z?\-]+)\s*(.*)$
if em:
    out.append((em.group(1).strip(), em.group(2).strip(), ts))
```
续行 `  BUILD_TAG=20261030-140212 account=...` **没有 `[P16SIG][EXEC]` 前缀** ⇒ `LINE_RE` 不匹配 ⇒ 这一行根本不进 `evts`。

而新增的 `pending_init` 分支在 `_summarize_events` 里等的是「下一条事件的 `rest` 里含 `BUILD_TAG=`」——**它等的那条事件永远不会被生产出来**。

### 3.3 后果

- 一旦 INIT 真打成多行，午间报告仍然渲染 `**无 INIT**`，并且仍然追加问题 `无 INIT（策略未启动/未加载）`。
- 与上一轮 §4.1 的判定**完全一致，没有变化**。这是同一条缺陷第二次被记为「已修」。
- `check_bridge_heartbeat._has_init` 那处是真修好了（`_model_lines` 返回原始行，含续行），所以三处里实际修好了两处：`check_running_tag`（上轮）+ `check_bridge_heartbeat`（本轮）。

### 3.4 P4f 为什么没抓到

`_test_reports_port.py:129-131`：
```python
check("P4f 午间 _summarize_events 支持多行 INIT（续行里的 BUILD_TAG）",
      MD._summarize_events([("INIT", "  BUILD_TAG=20261030-140212", "2026-10-30 08:52:25")])[0]
      == "20261030-140212")
```
两个问题叠加：
1. 它手造的事件 `rest` 里**已经带了** `BUILD_TAG=`，这是 `_scan_log` 永远产不出的形状（真实首行 `rest` 是空串）；
2. 正因为 `rest` 自带 TAG，`_summarize_events` 在 `kind=="INIT"` 的第一条正则就命中了，**`pending_init` 那段新代码一行都没执行**。

**这条测试既没测真实链路，也没测新代码。** 它测的是「`re.search` 能在字符串里找到 `BUILD_TAG=`」——这不是回归测试，是同义反复。

### 3.5 正确修法（二选一）

- **A（推荐）**：在 `_scan_log` 里做续行合并——归属命中后，若 `LINE_RE` 不匹配但行内出现 `BUILD_TAG=`/已知续行特征，就并入上一条事件的 `rest`（或产出 `("CONT", text, ts)` 事件），再让 `_summarize_events` 消费。
- **B**：`_scan_log` 直接负责把多行 INIT 拼成一行再产出。

无论哪种，P4f 必须改成**喂原始日志文本**跑完整链路，而不是喂事件元组。

## 4. ⚠️ `snapshot_missing` 在一个函数里有两个判据

## 7. 次要问题

### 7.1 `_has_init` 的三个分支全返回 True

`check_bridge_heartbeat.py` 的 `_has_init`：找到 INIT 行后，
```python
if "BUILD_TAG" in ln: return True
if i + 1 < len(lines) and "BUILD_TAG" in lines[i + 1]: return True

```
三条路径全 True ⇒ 等价于 `any("[P16SIG][EXEC] INIT" in ln for ln in lines)`。行为是 QD 想要的（「INIT 出现即算加载」），但前两个分支是装饰性的。**建议直接压成一行并保留注释说明「TAG 核对交给 check_running_tag」**——现在这样会让下一个读代码的人以为多行处理真的做了判断。

- G2：`src.find(...)` 比位置
- G3：`"args.plan_only and not args.date" in src`
- G4：`949 < 950`、`950 >= 950`、`"return 4" in src`

G4 前两条是**纯算术**，跟被测代码无关。这一套里真正有分量的是 G1（常量交叉核对）和 G5a/G5b（真跑 `main()`）。建议把 G4 删掉或改成边界真行为（`--plan-only` + hhmm=949 落盘、hhmm=950 不落盘），并把 G2/G3 标注成「源码形态断言」。

### 7.3 方向推断的两个边界

- **窗口外 ORDER 会丢方向**：`p16_close_report.py:171` 先按 `<= "15:10"` 过滤事件，再交给 `_summarize_events`。若某笔 ORDER 在 15:10 后、而它的 FILL 在 15:10 前（实际不会，但反过来的顺序在时钟异常时可能），方向会退化成 `"?"`，该腿判 ✘。今天不触发。

两条都属于「记一笔，不改」。

QD 反对「两个计划任务 `StartWhenAvailable=false`」，理由三条。我复核后**同意 QD，撤回我在上一轮 §6-3 的建议**。

理由核实：
1. **代码门确实是硬防护**：`.plan.json` 只由 `--plan-only` 路径写（`_save_plan:724-728`），而该路径已加门；`--live` 被接管标记堵死（`:666-669`）；dry-run 写 `.dryrun` 后缀。补跑再触发，写不坏任何被消费的文件。**成立。**
2. **`StartWhenAvailable=false` 会让「错过」变成「当天彻底没计划」**。QD 这条也对——而且比我上轮想的更要紧，因为 `--live` 兜底已经被接管标记关掉了，没有第二条腿能补出计划。
3. **「代码门 + 任务保持 True」是更稳的组合**。同意。

**但我要补一条 QD 没说的代价**：门卡在 `950`（= `EXEC_HM_START`），而执行窗口是 `950–958`。**09:50–09:58 之间写出来的计划本来是能被执行壳消费的**，现在一律 `return 4` 丢掉。也就是说，这个门把「晚 10 分钟的可用计划」和「晚 9 小时的有害覆盖」一起挡了。

更精确的写法是把门卡在 `EXEC_HM_END`（958），或者判「目标 `.plan.json` 今天已存在且已过 09:50 就不覆盖」。**这是设计取舍，不是 bug**，但 QD §9 只讲了「补跑无害」，没讲「正常晚点也无产出」，建议补进文档再定。

另外，门的条件 `args.plan_only and not args.date` 意味着 `--plan-only --date 20261030` 在 23:00 仍会写盘。如果这是给人肉复盘留的后门，应该显式注释；如果不是，应该去掉 `not args.date`。
