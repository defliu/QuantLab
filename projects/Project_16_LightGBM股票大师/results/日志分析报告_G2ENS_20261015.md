## 三、根因推断

### 3.1 直接根因：QMT 公式引擎受限模式（Foribdden FileIO 沙箱）

`PermissionError('Foribdden FileIO')` 的拼写（单 b 双 d）是 QMT 定制 `bin.x64\python36.dll` 内置的报错字符串，属引擎级文件 open 代理拦截：**客户端处于受限模式时，策略 Python 打开已存在文件（读或写）一律抛此错；新建文件不受影响；目录枚举不受影响**。本日志 13,970 次读失败全部命中该串，症状完全吻合。

### 3.2 排除其他假设

| 假设 | 排除依据 |
|---|---|
| 文件被其他进程锁住 | Windows 共享冲突应报 `winerror 32` 类 PermissionError，不会是 QMT 定制串 'Foribdden FileIO'；且两个策略、七个不同路径文件同时同报错 |
| 路径含中文 | `D:/QMT_POOL/...` 全 ASCII，无中文路径 |
| 文件缺失 | 全部为 PermissionError 而非 FileNotFoundError；STALE-CMD 的目录探测还能看到文件存在 |
| 磁盘/权限 ACL | 同一 Python 进程内目录枚举可用、仅 open 被代理拦截，不符合 OS 层 ACL 特征；符合引擎代理特征（正常态 `XtClient_Formula_*.log` 不出现 `python open file:` 行，受限态出现——见既有定性） |

### 3.3 触发链与本次会话定性

结合既有定性（2026-10-15 立 QMT 文件 IO 沙箱红线）：客户端每日 ~20:54 自重启，若重启时交易登录态不佳（晚间 20:15+ 券商维护窗口 relogin 失败），公式引擎进入受限模式且**进程生命周期内不解除**。

本日志证明：**14:00:56 重载策略后沙箱仍生效**——本次重载时客户端仍处受限态。两种可能（日志无法区分）：①只重载了策略、客户端进程未重启（进程不死沙箱不解除）；②客户端重启了但 70180771 交易登录未成功（登录不成功同样不解除）。恢复方法唯一：**完整重启 QMT 客户端并确认交易账号登录成功后重载策略**。

### 3.4 G2 刷屏 vs ENS 静默的差异

两桥同源构建但 fail-safe 行为迥异：G2 的 orders 轮询在读失败后**不退避、不转被动、不告警**，以 ≈330 次/秒持续硬撞；ENS 则 4 连败后零动作。差异根源在两者代码路径（轮询触发条件/时间窗检查/异常处理）不同，**需源码复核定位**，日志只能给出行为事实。

## 四、影响评估

### 4.1 当日换仓：未执行（两策略均漏）

- morning job 产出的 `orders_20261015.json` 在本日志窗口内 0 次读取成功（G2 13,958 次全败，ENS 0 次尝试）。
- 策略 14:00:56 才首次启动，09:3x 的换仓执行窗口早已错过——**G2/ENS 当日调仓指令 100% 未执行**。

### 4.2 漏单/重复单风险

- **当前窗口内零下单**，无已发生的重复单。
- 但存在高危组合：**「orders 未归档（stale 指令在盘） + INIT last_seq=0（去重水位清零） + positions=0（状态盲区） + G2 高频活跃轮询」**。一旦沙箱解除（客户端重启+登录成功）而策略未被重置/重载，G2 的轮询会立即成功读到 stale 的 morning orders 并可能照单执行：
  - 若账户实际持有旧仓而策略状态为 positions=0，买入指令会造成**重复建仓**（即已定性的「活跃实例 + 状态加载失败 + 持仓=0 盲跑」P0 形态，10-14 白天旧 build 已实证过其危害）；
  - orders 指令设计于 09:3x 执行窗口，14:00+ 执行属过期指令，价格/风控前提已失效。
- ENS 未进入轮询，风险敞口较 G2 小，但其 orders 同样未消费、状态同样全零。

### 4.3 其他影响

- **日志洪水**：42 秒 2.9MB，G2 报错淹没日志面板，ENS 与引擎信息被冲刷，排障信息密度极低。
- **观测盲区**：heart/peak 无法读写意味着桥接方（QuantLab 侧监控）也拿不到策略心跳/峰值状态，双向失明。
