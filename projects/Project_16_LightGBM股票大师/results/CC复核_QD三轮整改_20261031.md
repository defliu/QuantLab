## 3. 本轮新发现（3 条，均不阻塞）

### 3.1 `pending_init` 被「第一条 CONT」无条件消费，哪怕它没带 TAG

`p16_midday_report.py:182-186`：

```python
if pending_init:
    m2 = re.search(r"BUILD_TAG\s*=\s*([0-9A-Za-z._\-]+)", rest)
    if m2:
        init_tag = m2.group(1)
    pending_init = False        # ← 在 if m2 之外
```

探针实测：

| 事件序列 | `init_tag` |
|---|---|
| A 真实形态：`INIT` → `CONT BUILD_TAG=…` | `'20261030-999999'` ✅ |
| B `INIT` → `CONT account=…`（无 TAG）→ `CONT BUILD_TAG=…` | `''` ❌ |
| C 单行 `INIT BUILD_TAG=…` | `'20261030-888888'` ✅ |
| D 多行且全程无 TAG | `''`（正确，本就没有） |

**真实风险有多高**：主号日志里 G2 与 V13 共用同一个 FormulaOutput 流，而 QMT 只有 `print()` 的**首行**带 `reqid = 0<path>\python\<model>.py_NNN`（`MODEL_RE` 就靠它定归属）。另一模型的裸续行不带 `reqid`，`owner` 不会切换，于是被当成本模型的 CONT。若它恰好插在 G2 的 `INIT` 与 `BUILD_TAG=` 两行之间，TAG 就丢了。

**概率低、代价中**（丢了就是报告里「无 INIT」误报一次）。**一行可修**：把 `pending_init = False` 挪进 `if m2:` 内，或加「连续 3 条 CONT 未命中才放弃」。建议下一轮带上，不必为它单独开一轮。

### 3.2 `prev_was_event` 的注释与实现不符

`:137` 注释写「上一行是否属于本模型的一条 `[P16SIG][EXEC]` 事件」，但 `prev_was_event` 在 CONT 之后**不重置**，所以第 2 条及以后的裸行判据实际是「本模型块内出现过事件之后的任意非空裸行」。行为上无害（CONT 只喂 `pending_init`），但与 3.1 是同一个根因，改 3.1 时把注释一起改准。

### 3.3 `_test_v13_plan_timing.py` 的 V2 仍依赖本机计划任务

`:52-68` 通过 PowerShell `Get-ScheduledTask -TaskName 'Quant_P16_V13_PlanOnly_0936'` 读触发时点，任务不存在即 FAIL（`:66-68`）。这与 QD 刚修掉的「换天就挂」是同一类环境依赖，只是触发条件不同（换机器/换任务名才挂）。不影响本机，记一笔。

### 3.4（非缺陷）`_save_plan` 不是原子落盘

`rebalance_g2.py` `_save_plan` 用 `open(jp,"w")` + `json.dump` 直接写目标文件。若进程在写一半时被杀，会留下截断的 JSON，执行壳解析失败即静默当日无计划。属既有实现，与「已存在不覆盖」叠加后才值得关心（见 §4.2）。建议长期改成 `tmp + os.replace`。

## 4. 对 §7「门阈值 950 / 958」的答复

### 4.1 事实基础（我复核过的）

1. 执行壳窗口 `950–958`，窗口内 5 秒一轮询（§2.3 三条证据）。
2. `signal_id = 策略-日期-计划内容哈希`（`qmt_signal_hub.py:171`）⇒ **计划内容一变，sid 就变**。
3. 执行壳的去重是 `placed_sids` + `already_applied(sid, remarks)`（`strategy_p16_g2_exec.py:504/509/533`、`g2_signal_client.py:120-130`）——**只对同一个 sid 去重**。

第 2、3 条合起来意味着：**窗口内把计划换掉，壳会当成新信号再下一遍单**。所以 QD 说的「B 需要加『已存在不覆盖』」不是多余的谨慎，是必需品。纯粹放宽到 958 会打开双重下单的口子。

### 4.2 我的建议：选 B，按 QD 提的阈值原样落地

QD 的 `958` + 「当日 `.plan.json` 已存在且 mtime ≥ 09:50 ⇒ 不覆盖」，我核过它的边界：

| 场景 | 结果 | 对不对 |
|---|---|---|
| 09:40 正常跑，文件不存在 | 写入 | ✅ |
| 09:00 有人手动预览过（mtime 0900） | 09:40 覆盖 | ✅ |
| 09:40 漏跑，09:52 补跑 | 文件不存在 ⇒ 写入 | ✅ |
| 09:40 跑过，09:52 又补跑（内容不同） | mtime 0940 < 0950 ⇒ 覆盖 ⚠ | 理论上会双重下单 |
| 19:22 时钟跳变补跑 | 1922 ≥ 958 ⇒ 拒 | ✅ |

第四行是唯一残留。但它要求「任务 09:40 已成功、09:52 又被判定为错过并补跑」——`StartWhenAvailable` 的语义是「错过才补」，09:40 成功过就不会再触发。**该场景实际不可达**，因此不必为它再加复杂度。

**结论：A（保持 950）会白丢 09:50–09:58 的可用计划；B 的残留口子在调度语义下不可达。建议选 B，不要选更复杂的 C。**
