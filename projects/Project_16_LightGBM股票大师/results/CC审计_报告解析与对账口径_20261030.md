## 2. P0-1｜报告解析：续行盲区 + `FILL?` 当自有成交

### 2.1 缺陷 A：`key not in line` 丢掉全部续行

```
p16_midday_report.py:116    key = "%s.py" % model
p16_midday_report.py:119        if key not in line:
p16_midday_report.py:120            continue
```

QMT 的 `FormulaOutput` 日志格式是：**一条 `print()` 的首行带 `reqid = 0<路径>\python\<模型>.py_NNN, output = ` 前缀，多行 `print` 的后续行裸写**。
所以「模型名.py 出现在行内」这条判据只能命中每次打印的**第一行**。

今日实测：90 条事件行里 14 条是续行；**G2 全部 3 条 FILL、全部 2 条 ORDER 都是续行** → 报告对 G2 的「下单/成交」永远是 0 或残缺。

后果（今日实际渲染 vs 事实）：

| 项 | 报告（19:22 落盘） | 事实 |
|---|---|---|
| G2 主号 下单腿数 | 0 腿 | 2 腿（行 107/110） |
| G2 主号 603529.SH | 计划 800 / 成交 **300** ◐ | 计划 800 / 成交 **800** ✔ |
| G2 主号 300223.SZ | 计划 100 / 成交 **0** ✘ | 计划 100 / 成交 **100** ✔ |
| 报告「需关注」 | 列了「G2 主号 603529.SH 未完成、300223.SZ 未完成」两条**假故障** | 两条腿均已满额成交 |

即：**一天里两条腿全成，报告给出两条未完成告警。**

### 2.2 缺陷 B：`kind.startswith("FILL")` 把 `FILL?` 计为自有成交

```

p16_midday_report.py:141        m = FILL_RE.search(rest)
p16_midday_report.py:142        if m:
```

`FILL?` 在执行壳里的语义是**「这条成交不是我的，绝不回写」**（`strategy_p16_g2_exec.py:333`），
而报告用 `startswith("FILL")` 把它当自有成交累计。今日三块面板全部中招：

|---|---|---|---|

**沙箱那条最荒谬**：计划 100 股、报告「成交 300 股」并打 **✔**（`fv >= pv` 判超额完成），

这正是 `AGENTS.md:102`（「成交回写必须按 remark 归属，禁止扫全账号成交」）要防的串账，**执行层修好了，报告层又犯回去**。

### 2.3 缺陷 C：时间窗过滤对续行二次误杀

```
p16_close_report.py:94   _evts = [e for e in M._scan_log(log_dir, model) if e[2][11:16] <= "15:10"]
```

`e[2]` 是 `line[:19]`。续行的前 19 字符是 `[P16SIG][EXEC] FILL`（下标 0–18），
`[11:16]` 取到的是 `EC] F`，`"EC] F" <= "15:10"` 为 **False**（`'E'(69) > '1'(49)`）→ 即使修好缺陷 A，盘后报告仍会把续行全丢掉。

**修复缺陷 A 时必须同时修 :94，否则盘后仍是 0 成交。**

### 2.4 缺陷 D：回归用例的 fixture 比现实干净，所以全绿

```

```

fixture **没有任何续行、没有任何 `FILL?` 行** → 上述 A/B/C 三个缺陷在 10 个回归套件里全部测不出来。
这就是「改完测试全过、上线当天报告还是错」的机制性原因。

### 2.5 建议修复（供 worktree 交付）

1. `_scan_log` 改为**状态机**：命中 `reqid = 0...\python\<模型>.py_` 时进入该模型的归属态，命中其他模型前缀时退出；归属态内的裸行一律归当前模型。
   - 判据不要用 `key in line`，用正则 `re.search(r"\\python\\([A-Za-z0-9_]+)\.py_\d+", line)` 取模型名，做**等值比较**（顺带解决 `_G2_EXEC` 吃 `_G2_EXEC_SBX` 的隐患）。
2. `_summarize_events` 区分 `FILL` 与 `FILL?`：`FILL?` 单独计入 `foreign` 计数并渲染成「他人成交留痕 N 条」，**绝不并入 fills**。
3. `p16_close_report.py:94` 改为按归属态记录的**真实时间戳**过滤（首行取 `line[:19]`，续行继承上一条首行的时间）。
4. `_test_reports_port.py` 的 fixture 必须**照抄真实日志形状**：加入续行（ORDER/FILL 都不带前缀）+ 加入 `FILL?` 行 + 加入 V13 视角看 G2 成交的用例。
   建议直接从 `XtClient_FormulaOutput_20261030.log` 脱敏摘 20 行做 golden fixture，避免再手搓。
5. 顺带：`check_running_tag.py:71-72` 用的是同一套 `key = "%s.py" % model` 过滤。今日 INIT 行**恰好全部带前缀**（实测裸行里没有 INIT），所以运行态判定当前是对的——但这是**运气不是设计**，同一处也应改成状态机，否则哪天 INIT 打印成多行就会误判 `NOT_RUNNING`。

> ⚠ 边界：`p16_midday_report.py` / `p16_close_report.py` 不在 `build/` 下，可以改；但改动必须走独立 worktree + diff 交付，不要直接落 `master`。

### 3.3 缺陷 C：`snapshot_missing` 的守卫条件漏掉了「两边都空」

```

```

注释（:221-224）解释了「休市日 acct 空而账本非空 → 全负差额 → 误报」，所以加了 `and bool(ledger)`。
但**账本也空时**（今日正是如此）返回 `False`，于是「账户不可读」和「账户真空仓」两种状态在产物里**完全不可区分**，
下游一律按「无差额、无孤儿、无问题」渲染。

这直接违反 `AGENTS.md:156`「「账号不可读」≠「空仓」」。

### 3.4 缺陷 D（最危险）：死数据算出的权益被写进真实资金池

```
reconcile_g2.py:135   def _roll_g2_capital(date):
reconcile_g2.py:141       capital = G.START_CAPITAL + realized + float_pnl
reconcile_g2.py:145       G.save_g2_capital(round(capital, 2), note="reconcile 滚动 ...")
reconcile_g2.py:265   report["capital_rolled"] = _roll_g2_capital(date)
```

今日落盘（`D:/QMT_POOL/g2_bridge/g2_strategy_capital.json`，mtime 15:47:36）：

```json
{"account_id": "67014907", "capital": 93501.0,
 "note": "reconcile 滚动 realized=-6499 float=0", "updated_at": "2026-10-30 15:47:36"}
```

`realized=-6499` 来自 `_all_fills()`（`reconcile_g2.py:29-41`）遍历 state 目录里的历史 `fills_*.json`（最新 20261013），
`float=0` 来自 `_float_pnl_now()`（`reconcile_g2.py:105-132`）读 `positions_cfg`（最新 20261021）并配 `fetch_price`。
**两个输入都是 7–13 天前的死数据，输出却成了明天建仓预算的唯一依据。**

**今日算错的幅度（已核对口径，不大但方向明确）**：
`capital = START_CAPITAL + realized + float_pnl` 是**总权益**口径（`:141`），买入本身不减少权益，
所以今天买的 900 股（603529.SH 800@19.2662 + 300223.SZ 100@113.83，成本 26,796）**不会让权益凭空多出 2.7 万**。
真实的错是：`float_pnl=0` 因为持仓不可见 → **今天这 900 股的浮动盈亏完全没计入**（今日成交价 19.26/19.27/113.83，
与成本 19.2662/113.83 几乎持平，所以**今日偏差很小，量级在百元内**）。

**但偏差会随时间放大**：这 900 股在 G2 账本里会一直「看不见」，只要 state 目录不恢复，
后续每一天的浮盈/浮亏都不会进入 `capital`。持有 15 天后卖出时，`realized` 也照样算不到这笔。
**所以问题不是今天错了多少，而是这个数会永久性地偏离真实权益，且没有任何告警。**
（`realized=-6499` 本身取自 20261013 之前的历史 fills，属真实历史值；`float=0` 是缺当日快照导致的 —— 两者混在一起无法区分。）

`g2_config.py:90-104` 的 `read_g2_capital()` 会**优先读这个文件**（account_id 戳校验通过），失败才回退 `START_CAPITAL=100000`。
今日 G2 计划 `capital: 93501.0`（`data/rebalance_g2/rebalance_g2_20261030.plan.json`）即由此而来。

### 5.3 心跳日志 43 个里 39 个是纯噪音
