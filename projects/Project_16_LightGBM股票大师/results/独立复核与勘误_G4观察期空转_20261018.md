（L200，第一条未回填）

- **2026-09-17 / 09-18 / 09-21 / 09-22 / 09-23 的候选行均带完整 entry/exit/ret**（可见 L135-137、L138-151、L152-167、L168-183、L184-199）；

## 二、勘误②：机制表述——不是"后续步骤从未执行"

**既有报告 §二第 2 条的表述**（本报告初版亦照抄，故一并更正）：「`build_g2_daily.py` 立即失败 → … → `exit 2`，后续全部步骤（含 `paper_forward.py --backfill`）**从未执行**」。

**该表述与同段括号内自述矛盾**：括号写「日志中 `No module named 'encodings'` / `Fatal Python error` 各出现 **40 次**（**每个步骤各崩一次**）」。

**实测复核（ps1 控制流）**：`paper_forward_daily.ps1` 的 8 个步骤全部写在同一个 `try { … }` 块内（L62-82），退出码检查在 `Pop-Location`（L82）**之后**（L83-113）。

⇒ **正确机制**：**8 个步骤全部执行、且全部在解释器启动阶段崩溃**（40 次致命错 ÷ 5 个失败交易日 = 每天 8 步，与"每个步骤各崩一次"吻合）；ps1 直到全部步骤跑完才按退出码 `exit 2`。

**这个更正改变了一条教训（重要）**：

| | 错误理解 | **正确理解** |
|---|---|---|
| backfill 为何无产出 | ps1 早退，第 3 步没跑到 | **跑到了，但解释器起不来，脚本连第一行都没执行** |
| 为何 fail-loud 没救场 | ps1 早退把 fail-loud 短路 | `paper_forward.py` **自带**的两道 fail-loud（L192-195：`stale→exit 2`、`total>0 且 done==0→[ALERT]`）**在解释器损坏时无法存活**——它们本身就跑不起来 |
| 教训 | "fail-loud 要放在被依赖步骤之前" | **"脚本内部的 fail-loud 无法防御解释器级故障"** → 守卫必须放在**包装层/调度层**（正是修复项①`Get-GoodPy` + `PY-ALERT` 的做法，方向正确） |

> 附带说明：这也解释了"候选行为何涨到 10-12"——由 20:05 的 `g2_candidates_night` 腿追加（既有报告已写明，本报告复核认可）。

## 三、补充：文件系统级独立证据（既有报告未提供）

既有报告的证据来自**日志自述**。本报告补一项**不依赖日志**的证据：

`LS C:\Users\Administrator\AppData\Roaming\TRAE SOLO CN\ModularData\ai-agent\vm\tools\python\` → 该目录**仅剩 13 个文件**：

```
python.exe / python3.dll / python310.dll / vcruntime140.dll
_bz2.pyd / _hashlib.pyd / _lzma.pyd / _socket.pyd / _ssl.pyd / select.pyd / unicodedata.pyd
libcrypto-1_1.dll / libssl-1_1.dll
```

**没有 `lib/`、没有 `DLLs/`、没有 `python310.zip`、没有 `site-packages`。**

`encodings` 是标准库包（位于 `lib/encodings/`）→ **物理上不存在** → `Fatal Python error: init_fs_encoding` 是必然结果。日志 `sys.path` 里声明的三个路径（`python310.zip`、`.\DLLs`、`.\lib`）**全部不存在**，与文件系统一致。

⇒ 结论：**"解释器损坏"从日志自述升级为文件系统级实证**，且解释了它为何表现为"**间歇性**"（既有报告 §二注已推测）：若 TRAE 侧曾短暂回填 `lib/` 又移除，即可解释 09-30~10-09 能跑通、09-28 与 10-12 起崩溃。
