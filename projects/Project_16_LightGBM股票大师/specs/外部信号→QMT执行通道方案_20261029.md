# 外部模型 → QMT 内执行：信号通道方案（2026-10-29）

> 一句话：**模型和特征留在外部（Python 3.11 + `D:/astock` + LightGBM），QMT 内置策略只当「执行壳」**——
> 通过**回环 HTTP** 取一份带信封的换仓计划，校验后 `passorder`，把成交/拒单原因 `print` 回日志。
> 这条路绕开了内置侧拿不到财务/股本数据的天花板，也不依赖 miniQMT 授权。

---

## 一、为什么必须把信号搬到外面（问题陈述，均有实测依据）

内置 21 特征引擎「信号内产」版早已上线，但 `SIGNAL_ENABLED=False` 一直没敢打开，原因是**数据面残缺**，
不是代码写错（2026-10-27 v4.7 探针实证）：

| 内置可用性 | 字段 / API | 实测结论 | 对 21f 的影响 |
|---|---|---|---|
| ❌ | `get_finance` | `'__main__.ContextInfo' object has no attribute 'get_finance'` | 直接不可用 |
| ⚠️ | `get_financial_data` 7 字段 | 形状正常、**值全 nan**（本地财务数据包未下载） | F2/F5/F6 拿不到 |
| ⚠️ | `get_instrument_detail.FloatVolume` / `get_total_share` / `get_float_caps` | 20 只样本仅 **2 只**在 1% 内，18 只偏 1.6%~100%（2 只返回 0） | `float_share` → `true_turnover` → 污染 `turn_ma5` / `turnover_rank` / `log_mv` |
| ❌ | `get_turnover_rate` / `get_turn_over_rate` | 批量返空表 / 单票 `nan` | 换手率类特征不可信 |
| ✅ | `get_market_data_ex` / `get_full_tick` | 可用，数据日期比本地 astock **新 2 个交易日** | 只够算价量类特征 |

结论：**内置端不缺算力、缺的是「干净的特征源」**。与其在 3.6 的内置环境里重造财务/股本口径，
不如让外部把特征、模型、组合权重全算完，只把**结论**送进来。

## 二、通道选型（为什么是回环 HTTP）

| 方案 | 实测状态 | 结论 |
|---|---|---|
| 文件桥（`D:/QMT_POOL/cmd`、JSON 读写） | 内置 `open()` 读一律 `Foribdden FileIO`，写时开时拒（10-20/10-26 两次复测） | **出局**，不可再投资 |
| KV `save_py_key/get_py_key` | 仅小数据（1MB 起静默丢），且**写入端必须是策略进程自己**，外部写不进去 | 出局（无法当入口） |
| sqlite（外部写库、内置读） | sqlite 在沙箱可用（走自身 C 层 IO、跨重启持久），但「外部写 + 内置主线程读」**未实测** | 备选/降级，不作主线 |
| **回环 HTTP** | 网络位全开：回环/`127.0.0.1:58600`/HTTP/HTTPS 通，`requests 2.24.0` 与标准库 urllib 都可用 | **主线** |

选 HTTP 的额外好处：外部进程与策略进程**完全解耦**——hub 死了只是「没有信号」，不会留下半截文件；
而且执行结果可以按同一通道回传（下一阶段），不需要再开一条新路。

## 三、架构

```
[外部 · Python 3.11]                                [QMT 内置 · Python 3.6]
 D:/astock 全量数据                                  执行壳（薄）：
   ↓ 特征/评分/LightGBM                              handlebar → 每 N 秒最多轮询一次
 rebalance_g2.py → plan{orders:[...]}                   ↓ GET http://127.0.0.1:58610/signal
   ↓ 落盘 data/rebalance_g2/rebalance_g2_<date>.json      ↓ 校验（schema/日期/账号/过期/字段/去重）
 qmt_signal_hub.py（只读转发，绑 127.0.0.1）  ────────→   ↓ 通过则 passorder（remark=signal_id-...）
   ↑ 计划文件 mtime 变化即生效                            ↓ 每腿 print [P16SIG] 结果（供旁路采集）
```

**职责切分（防「又变成两套决策」）**：外部只产 `plan`，不接触账户；内置只执行，不修改 `plan`
（剪枝/跳过必须回日志，不能静默改单）。

## 四、契约 `p16.signal.v1`

```json
{
  "schema": "p16.signal.v1",
  "signal_id": "g2-20261029-<计划内容sha8>",
  "trade_date": "20261029",
  "account_id": "67014907",
  "strategy": "g2",
  "capital": 100000.0,
  "generated_at": "2026-10-29 09:29:58",
  "served_at": "2026-10-29 09:30:02",
  "served_ts": 1793... ,
  "source": "rebalance_g2_20261029.json",
  "orders": [
    {"action": "SELL", "code": "600000.SH", "vol": 100, "price": 9.78,
     "reason": "rotate_out", "strategy_order_id": "g2-s1"}
  ],
  "meta": {"n_orders": 1, "written": true, "note": ""}
}
```

**幂等键**：`signal_id = 日期 + 计划文件内容 sha8`。同一份计划重复发布得到同一个 id ⇒ 内置侧天然
去重；重启后重放也不会重复下单。跨重启的真相源是**当日委托 remark**（`already_applied()`），
不是内存变量。

**校验（任一不过 ⇒ 整单放弃，不部分执行）**：

| 检查 | 不过时 |
|---|---|
| `schema` 必须等于 `p16.signal.v1` | 拒绝 |
| `trade_date` == QMT 当日（`C.get_current_time()` 的日期） | 拒绝（防隔夜重放） |
| `account_id` == 策略配置账号 | 拒绝（防串号，同「持票账本必须内嵌 account_id」） |
| `now - served_ts ≤ max_age_s`（默认 600s） | 拒绝（防拿上午的信号在下午执行） |
| `orders` 非空 | 拒绝——**空订单不等于清仓** |
| 每条 `action∈{BUY,SELL}`、`code` 匹配 `\d{6}\.(SH|SZ|BJ)`、`vol>0 且整百`、`price≥0` | 拒绝 |
| 同 `(action, code)` 不重复 | 拒绝 |

**fail-safe 总原则**：hub 不可达 / 超时 / 404 / 字段非法 ⇒ **本轮不下单，下个 tick 再试**，
且每轮只打一行 `[P16SIG][REJECT] 原因`，不刷屏、不抛异常、不把异常冒到 QMT 引擎。

## 六、执行壳的设计约束（下一步实现，不能省）

1. **轮询节流**：`handlebar` 里用 `time.time()` 记上次拉取时刻，间隔 ≥5s；一次拉取 `timeout` ≤2s，
   绝不让 HTTP 卡住 `handlebar`（否则盘中行情回调全被拖慢）。
2. **账户即真相**：下单前按 `get_trade_detail_data(acct,'STOCK','position')` 校准可卖量；
   不读任何文件、不依赖内存账本。
3. **remark 打 sid**：`remark = signal_id + "-" + leg_index`，既是审计也是跨重启去重键。
4. **时段闸保留**：下单前校验 09:30–11:30 / 13:00–14:57；收盘后一律拒绝（AGENTS 实盘执行红线，
   2026-10-22 收盘后「已成」次日复活的教训）。
5. **不做的事**：不撤单重试（第一版）、不做部分成交补偿、不追单；这些都是 V1.3 xtquant 腿的职责，
   两套不要混。

## 七、部署与调度

- **外部 hub**：`Quant_P16_SignalHub`（每日 09:15 起，收盘 15:10 后自停，S4U 可，因为它不碰 GUI）。
  进程起不来 = 没有信号 = 不下单，不产生风险。
- **执行壳**：按零介入流程 `qmt_autodeploy.py --model STRATEGY_P16_G2_EXEC` 落盘 + 重启；（新模型名需先在
  客户端注册一次）。**它与现有 `STRATEGY_P16_G2_SELFCONTAINED`（自算 21f，passive）并存，互不干扰**；
  上线时确认只有执行壳 `passive=False`。
- **监控**：`[P16SIG]` 行由沙箱外旁路读 FormulaOutput 推飞书（沿用现有监控，不需要策略进程做 IO）。

## 八、与 2026-10-15 长期红线的关系（必须显式说明）

10-15 红线原文要求「交易信号完全在 QMT 系统内部产生、不与外部环境进行任何交互」。
本方案**信号在外部产生**，与该条冲突；但：

- 10-19 已因同一类现实约束修订过红线（xtquant 外部进程解禁、V1.3 继续用外部下单），说明
  「信号内产」在数据面残缺时无法执行；
- 本方案比 xtquant 外部下单**更收敛**：下单仍在 QMT 内（`passorder` 原生、账户上下文原生），
  不依赖 miniQMT 授权（70180771 未开通也能跑），也不受「券商移除 miniQMT」的行业趋势影响；
- 建议把红线改写为：**「下单动作必须在 QMT 内完成；信号可来自本地回环，但不得访问公网、
  不得写策略侧文件」**——即「执行内、信号近」。

**待诚哥拍板**：是否按上述改写红线；若坚持「信号必须内产」，则在客户端补下本地财务数据包
（`get_financial_data` 由 nan 变有值）后重跑 v4.8 探针，看能否把 21f 救回来——那是另一条路，
可与本方案并行验证，不冲突。

## 十一、执行时刻与双账号部署（2026-10-29 04:3x，诚哥拍板「同票双买没问题，做好账；错不错开你判定」）

### 11.1 判定：**不需要为「同票双买」错开，但必须把执行锁进 09:50–09:58 窗口**

先摆事实（都从代码里读出来的，不是推测）：

| 策略 | 回测成交口径 | 实盘既有确认口径 | 出处 |
|---|---|---|---|
| G2 | **开盘价** | **09:50 触发、09:58 未成当日放弃** | `backtest_b21_strategy.py` L26；`build/...selfcontained.py` 的 `SIGNAL_HM="09:50"` / `SIGNAL_DEADLINE_HM="09:58"` |
| V1.3 | 09:45 批次 | **09:45 主任务 + 10:05 guard 兜底** | `rebalance_daily.py` L214 |

**所以判定是**：

1. 执行壳锁 **09:50–09:58**，与 G2 既有口径逐字一致 —— 这是「与回测同口径」的唯一正确做法。
   修复前的执行壳只要「在连续竞价时段」就会下单，10:30 收到信号也会照单执行，**那已经脱钩了**，
   本轮已改为 `EXEC_HM_START=950 / EXEC_HM_END=958` + `in_exec_window()`。
2. **不需要为 V1.3 额外错开**：V1.3 的 09:45 批次与 09:50 相隔 5 分钟，市价单通常已成交；
   人为把 G2 推到 09:55/10:00 反而**拉大了与「开盘价」口径的偏差**，属于为了躲冲突而牺牲口径。
3. 同票竞争的处置改成**留痕**：卖腿可卖量不足时打 `TRIM code 300->200(可用=200)`，
   完全无可用量时打 `SKIP code 无可用量(计划=300)`，**不再静默缩量**——次日对账一眼能分出
   「账户竞争」和「信号错误」。
4. 两边同票都买：已拍板允许，因为两个策略各有独立 `capital_base` 与成交账本
   （`g2_bridge` / V1.3 各自 10 万），对账按账号+策略分开记。

### 11.2 双账号拓扑（建议即按此部署）

| 位置 | 账号 | 跑什么 | 资金 | 信号端口 | 定位 |
|---|---|---|---|---|---|
| **主号** `D:\国金QMT交易端模拟` | 67014907 | V1.3（xtquant 09:45）+ **G2 执行壳**（内置 passorder 09:50） | 各 10 万 | 58610 | **生产**（证据链在此） |
| **沙箱** `D:\QMT交易端模拟` | 70180771 | **G2 执行壳灰度**（同一份产物、不同账号/端口/资金） | **2 万** | 58611 | **灰度位**：验证执行链路，不计前向业绩 |

理由（按重要性）：

1. **V1.3 只能放主号**——70180771 未开通 miniQMT（`subscribe()` 返 -1、`query_stock_asset()` 返 None，
   2026-10-22 实测），xtquant 腿在沙箱根本连不上。
2. **执行壳放沙箱做灰度最合适**——它不依赖 miniQMT（内置 `passorder`），沙箱又免时段闸、可随时重启，
   且不承载任何「干净交易日」证据 ⇒ 拿它当第一次真单的试验场，出事只脏一个不重要的账号。
3. **不要把两个策略拆到两个账号做「隔离」**——那会把 V1.3 判死（miniQMT 限制），
   而真正的隔离已经由「账本 + capital_base」实现了；账号层面的隔离只用于**生产 / 灰度**分离。
4. **同一 signal_id 在两个账号各执行一次是预期的**：沙箱那份只用 2 万，不进前向统计。
   若不想双执行，把沙箱那份保持 `DRY_RUN=True` 即可，零成本。

### 11.3 构建与部署（两条命令）

- **Start 的坑（本轮实测踩到）**：不能用 `Start-Process` 起 hub——子进程会被计划任务的 job 收编，
  任务于是「一直在运行」（`LastTaskResult=0x41301`），30 分钟 `ExecutionTimeLimit` 一到会把 hub 一起
  TERMINATE 掉（表现为 09:45 信号通道突然消失）。改用 `Invoke-CimMethod Win32_Process Create`，
  进程父级落在 `cmd.exe`/services，任务立刻以 0 结束。回读实证：`result=0 state=Ready`，
  两实例各一个 python 进程、父进程为 cmd.exe。
