## 一、结论速览

| 问题 | 结论 | 证据 |
|---|---|---|
| `python\` 下的**明文** .py 会被客户端执行吗？ | **会**（旧红线「直接复制到运行目录无效」被推翻） | 用明文探针覆盖 `STRATEGY_P16_G2_SELFCONTAINED.py` 后重启，`XtClient_FormulaOutput_20261028.log` 产出 `CANARY2 hits 56396` 行，含 `[CANARY2][INIT] BUILD_TAG=CANARY-PLAINTEXT-1548` 与连续 `[CANARY2][HB] ... barpos=56393` |
| 客户端会把明文文件重新加密/还原吗？ | **不会** | 228 字节探针（md5 `10a5a0c6560733745ba150d23a095f6c`）跑完整一轮、并 `Stop-Process -Force` 杀掉后，文件 md5 不变 |
| 新增模型名能靠改 XML 注册吗？ | **不能** | 向 `indexUserConfig.xml` + `formulainitstepsinof` 插入 `CANARY_DEPLOY` 后重启，客户端日志：`configFormula not exist, continue. ... utfName:CANARY_DEPLOY` → 仅 `auto run timeout`，**零 Python 输出** |
| 模型名必须满足什么前提？ | **必须已在客户端注册过**（`indexConfig/configFormula`，二进制 `XTF1`，1 296 464 字节，模型名不以 utf-8/utf-16-le/gbk 明文存放，不可安全编辑） | 同上；G2/ENS/V2/V13 等现有模型全部可被明文覆盖后正常执行 |
| `auto run timeout` / `loadFile [X] parse error` 是错误吗？ | **否，属正常噪声** | G2 每次重启都会打印这两条，同时正常运行、`passive=False/True` 心跳不断 |
| 重启客户端要带参数吗？ | **必须带 `reboot`** | 不带参数启动会停在 `[LOGIN] Proxy client not logged`（每 5s 一次）+ `slot_timeoutShow update timeout`，**一个策略都不跑**（PID 8600 实测）；带 `reboot` 后自动登录并拉起全部 autorun 策略 |
| 沙箱（`Foribdden FileIO`）会挡住这条路吗？ | **不会** | 沙箱拦的是**策略进程内部**的 open/read；客户端自身的编辑器/加载器读 `python\*.py` 不经过该拦截 |

**一句话**：沙箱封的是策略的 IO，不是客户端加载策略的 IO —— 这两件事必须在脑子里分开。

## 二、机制原理

```
build_xxx.py  ──►  build/<产品>.py (GBK, BUILD_TAG=YYYYmmdd-HHMMSS)
                        │
                        │ ① 直接写文件（无需客户端在场）
                        ▼
        <QMT>\python\<模型名>.py        ← 与客户端「策略编辑器保存」落盘位置相同
                        │
                        │ ② 重启客户端：XtItClient.exe reboot
                        ▼
        [AutoRunStrategy]Account:xxx, strategyname:<模型名> automatic run
                        │
                        │ ③ 客户端用自己的加载器读 python\<模型名>.py
                        ▼
        userdata\log\XtClient_FormulaOutput_<yyyyMMdd>.log
                        │
                        │ ④ 脚本轮询日志，匹配 BUILD_TAG=<期望值>
                        ▼
                    PASS / FAIL
```

模型名与文件名严格一一对应：日志里 `reqid = 0<path>\python\<模型名>.py_<id>` 可直接印证。

## 三、前置条件（每个策略一次性）

**模型名必须在客户端里"存在过"**。做法（一次性，约 1 分钟）：

1. 打开 QMT → 策略编辑器 → 新建策略，名字 = 你想要的模型名（如 `STRATEGY_P16_G2_SELFCONTAINED`）；
2. 内容随便是 `print("x")` 即可，保存；
3. 之后**所有**部署都可以走 `qmt_autodeploy.py`，再也不用打开编辑器。

> 为什么不能脚本化注册：注册信息在 `indexConfig\configFormula`（二进制 `XTF1`），模型名不以任何明文编码出现在其中，盲改有极高概率损坏整个策略列表。不值得为「省一次 1 分钟的人工」冒破坏客户端的险。

现有已注册、可直接被自动化覆盖的模型名（70180771 客户端）：
`STRATEGY_P16_G2_SELFCONTAINED`、`STRATEGYV2`、`STRATEGY_ATR_LOWVOL`、`QMT_SANDBOX_PROBE` 等（`python\` 目录下可见者基本都已注册；以重启后日志有无 `configFormula not exist` 为最终判据）。

## 四、操作手册

脚本：`projects/Project_16_LightGBM股票大师/qmt_autodeploy.py`

```bash

    --model STRATEGY_P16_G2_SELFCONTAINED --qmt-dir "D:\QMT交易端模拟" --dry-run

# 2) 完整链路：构建 → 校验 → 备份 → 落盘 → 重启 → 等 BUILD_TAG
python qmt_autodeploy.py --build build_p16_g2_selfcontained.py \
    --product build/strategy_p16_g2_selfcontained.py \
    --model STRATEGY_P16_G2_SELFCONTAINED --qmt-dir "D:\QMT交易端模拟"

# 3) 只落盘（等客户端 20:54 自重启或下次开机生效）
python qmt_autodeploy.py --product build/strategy_p16_g2_selfcontained.py \
    --model STRATEGY_P16_G2_SELFCONTAINED --qmt-dir "D:\QMT交易端模拟" --no-restart
```

脚本内置的护栏：

| 护栏 | 行为 |
|---|---|
| **交易时段闸** | 09:00–15:05 一律拒绝重启（含午休），退出码 2；`--force-offhours` 才能越过 |
| **进程隔离** | 只杀 `ExecutablePath` 落在 `--qmt-dir` 下的 `XtItClient.exe`，**绝不会误杀另一台客户端**（国金生产端） |
| **先优雅后强杀** | `CloseMainWindow()` 等 12s，不退出再 `Stop-Process -Force` |
| **产物校验** | 拒绝 BOM、非 GBK、首行非 `# coding=gbk`、取不到 `BUILD_TAG` 的产物（退出码 3） |
| **自动备份** | 旧模型备份到 `_deploy_bak/<模型名>.<时间戳>.py`，滚动保留最近 10 份 |
| **判定不用噪声** | `auto run timeout`、`loadFile parse error` 不作为失败信号；只认 `BUILD_TAG=<期望值>` |
| **未注册诊断** | 日志出现 `utfName:<模型名>` + `configFormula not exist` → 直接报 `MODEL_NOT_SEEDED`（退出码 4）并给出补救说明 |

退出码：`0` PASS / `2` 时段拒绝 / `3` 产物非法 / `4` 未出 TAG（或模型未注册）/ `5` 重启失败 / `6` 环境错误。

## 六、局限与风险

1. **模型名必须预注册**（见 §三）——每个新策略一次性人工 1 分钟，之后全自动。
2. **重启代价**：重启客户端会中断当前所有策略（本机 70180771 仅 G2 passive，代价≈0；**国金生产端有三条策略在跑，重启必须按非交易时段 + 盘中不重启**）。脚本的时段闸默认覆盖这一点。
3. **优雅关闭不可靠**：QMT 主窗口对 `CloseMainWindow()` 基本无响应，实测 12s 后仍存活 → 走强杀。强杀对自闭环策略（账本 = 账户 position）无非交易时段风险；**但盘中强杀会让当根 K 线的 handlebar 丢失**，因此盘中重启一律禁止。
4. **数字签名/自检未知**：未观察到客户端对明文文件做 hash 校验或加密回写；若未来版本加入，本方案会在「重启后不出 TAG」处显性失败（不会静默跑旧版本——因为 TAG 不匹配即 FAIL），届时退回人工粘贴。
5. **必须核对 TAG**：不要只看"进程起来了"。本脚本 PASS 的唯一判据是日志里的 `BUILD_TAG` 等于产物里的 `BUILD_TAG`。

### 9.2 判定与退出码

- 体检只统计 `deploy_start` **之后**的日志记录——开机时的旧告警（如早上那批 `INIT-SNAP-ERR`）不会污染本次判定。
- 分级：`configFormula not exist` / `Foribdden` / `PermissionError` / `Traceback` → **critical**（`Traceback` 若同时出现 `passive=True` 则降级 attention）；`INIT-SNAP-ERR` / `INIT-REBUILD-ERR` → attention；`auto run timeout` / `parse error` → 噪声。
- 退出码：`0` OK / `2` 时段拒绝 / `3` 产物非法 / `4` 未出 TAG / `5` 重启失败 / `6` 环境 / `10` 部署 OK 但体检 FAIL。

### 9.3 本轮修掉的三个真 bug（都会在无人值守时造成假失败/漏杀）

1. **`start_client()` 假失败**：旧实现 `sleep(3)` 后只查一次 PID。单实例交接（先起一个进程 → 自查已有实例 → 自杀 → 由存活实例接管登录）期间进程可能根本不可见或 PID 会变 → 误报「启动失败」而客户端其实在起。改为**最多等 90s 轮询、连续可见 8s 才确认成功、并排除刚被杀掉的 PID**。
2. **`ps_run()` 编码错配（最隐蔽）**：`qmt_nightly_deploy.ps1` 为写日志把 `[Console]::OutputEncoding` 设成 UTF-8，而它是**控制台级**设置（`SetConsoleOutputCP`），同一控制台里派生的子 PowerShell 也跟着吐 UTF-8；`qmt_autodeploy.ps_run()` 却一律按 GBK 解 → 中文路径 `D:\QMT交易端模拟` 解成乱码 → `list_client_pids()` 的 `startswith` 比对失败 → **返回空列表：既杀不到旧进程，也认不到新进程**，日志表现为「全程未见进程」而任务管理器里客户端明明活着。修法：`ps_run` 在脚本前置 `[Console]::OutputEncoding=UTF8`，解码先 `utf-8` 再 `gbk` 兜底。**注意：直接 python 调用时正常、走 ps1 时才复现——所以「单独跑过没问题」不能作为这项的验收。**
3. **ps1 回显乱码**：`latest.json` 的一行回显发生在 `[Console]::OutputEncoding` 已还原之后 → 中文 verdict 变乱码。改为**所有 python 调用结束后**再还原。

### 9.5 演练与失败处置

- 演练：`powershell -File qmt_nightly_deploy.ps1 -Rehearsal` → 走 `--deploy-dry-run`，**既不落盘也不重启**（不能用 `--no-restart`：那会把新产物写进 `python\` 但不重启加载，造成「盘上 TAG ≠ 运行中代码」的失真状态）。演练报告落名为 `REHEARSAL_<戳>.md/json` 且**不覆盖 `latest.json`**，补跑任务不认它（详见 §10.5④）。
- 登录前置闸（2026-10-29 加，T-20261029-002）：`qmt_nightly_deploy.ps1` 在**非演练**时先跑 `scripts/qmt_login_probe.py --verdict --client D:\QMT交易端模拟`，rc=2（进程在跑但未登录）⇒ **整轮跳过**（不 build/不落盘/不重启），记一行 `WAIT` 后 `exit 0`，不残留部署锁；rc=4（进程不在）**不拦**，交给 `qmt_autodeploy` 带 `reboot` 拉起（那才是恢复路径）。理由：未登录时 `handlebar` 永不触发，硬跑必然 rc=4「未出 BUILD_TAG」，白耗一次客户端重启、还产出一条假 FAIL 覆盖 `latest.json`（21:10 定时任务在券商维护窗口里每晚都会这样污染一次判定链）。实测 01:23:49：`WAIT 沙箱未登录…EXIT=2`、`deploy_exit=0`、两台客户端进程数仍为 2（未被重启）、`qmt_deploy.lock` 无残留、`latest.json` 保持 00:23 那份真 FAIL。**只有 rc=2 会拦**（rc=0 放行；探针自身报错等其它码一律放行并记一行 `PROBE rc=…`）——这是故意的 fail-open：这个闸的全部作用只是省掉一次注定白耗的客户端重启，不该升级成闭环的新单点，探针坏了顶多退回旧行为（跑一轮、出假 FAIL），而误拦会让券商恢复当晚也补不出 PASS。
- 失败：看 `data/schedules/qmt_nightly.log` 尾部 → `results/qmt_nightly/latest.json` → 按退出码定位（4 = 未出 TAG，先查模型是否已注册、再看 `XtClient_FormulaOutput_*.log` 有没有 `configFormula not exist`）。

## 十、登录态前置依赖与自动补跑（T-20261029-002，2026-10-29 立）

> 闭环的隐含前提是**客户端已登录券商账号**。未登录时 `handlebar` 永不触发 → `FormulaOutput` 里不会出现新的 `BUILD_TAG` → 部署退出码 **4**（看起来像"部署坏了"，其实是登录没了）。§十把这条依赖变成**可判定 + 可自动补跑**。

### 10.1 2026-10-29 事故定论：券商侧登录服务不应答，本机无解

夜间闭环 `21:10` 与补跑 `00:23` 两轮均 rc=4（`20261028-211001`、`20261029-002304`）。逐层排除后的**权威结论**：

| 层 | 实测 | 判定 |
| --- | --- | --- |
| 网络 / TCP | `180.169.107.19:56001` **00:03 起可达**，客户端 `onConnected … remote_addr = 180.169.107.19:56001` 反复成功 | ✅ 通 |
| 客户端 | 带保存的凭据**自动重试**：`slot_doLogin → status 4 连接中 → 5 已建立连接 → 6 登录中`，失败后 ~12s 再自动来一轮 | ✅ 正常，无需人工点 |
| 券商 xtservice（应用层） | 登录前置四个 RPC **全超时**：`onSecurityCodeEnabled`（获取验证码权限）、`onDefaultServerParam`、`onGetLoginAdvert`、`onGetPinImage` → 均 `ErrorID: 200003, ErrorMsg: "超时"`，随后 `onLogin status = 21 登录失败` | ❌ **死在这里** |
| 本机 / 凭据 / 验证码 | 登录框账号密码在位、无验证码、`customer.lua` 地址正确（未改动）；主号与沙箱**同机同刻同样报错** | 排除 |

**要点三条**：

1. **`200003 超时` ≠ 拒连**。拒连是 `login status: 1 由于目标计算机积极拒绝`（10-28 深夜那一轮）；`200003` 是 TCP 已连上、报文 120 秒无应答。**两种都属券商侧，处置动作不同**：拒连 = 端口没起（`Test-NetConnection` 就会 False）；超时 = 端口起了但服务没就绪（探测端口会是 True，**极易误判成"服务恢复了"**）。
2. **人工点「登录」没有用**（本条推翻 00:20 的临时判断）。客户端本来就在自动重试，人工点只是插进同一队列；柜台不应答时，手点同样 120s 超时。
3. **`doSwitchXtservice new addr: 180.169.107.19:56001`（换了个相同地址）** —— 客户端支持服务端下发备用登录节点，但备用列表来自 `queryDefaultServerParam`，而该调用本身超时 ⇒ **自动故障转移在此刻不可用**。`customer.lua` 里的 `xtaddress.proxy = 81.69.152.51:59001 / 迅投上海主站:43.242.96.162:55300` 是**代理**地址（另一通道，不是登录节点的替换项）；手工改写登录地址属未验证路径，**动之前需诚哥拍板**。

**旁证（00:51 实测，判"整片维护"而非"单点故障"）**：同一台机器、同一时刻对 `customer.lua` 里四个端点做 TCP 探测 ——

| 端点 | 结果 |
| --- | --- |
| 登录/xtservice `180.169.107.19:56001` | TCP OK（但应用层不应答，见上） |
| proxy `81.69.152.51:59001` | TCP OK |
| proxy 迅投上海主站 `43.242.96.162:55300` | TCP OK |
| **行情 `xtquoter_address 175.25.41.69:55300`** | **FAIL（connect 超时）** |

⇒ 登录节点端口开着而服务无应答、**行情节点连 TCP 都握不上**，两条独立服务同时异常 ⇒ 券商模拟环境整体维护/故障窗口，不是本机网络或客户端配置问题。**推论**：恢复时刻不可预测，只能靠自动补跑守；且登录恢复后行情可能仍滞后，G2 在沙箱本就 passive，不影响 PASS 判定（判定只认 `BUILD_TAG`）。

**穷举核对（01:40，`scripts/_qmt_node_scan.py`，只读：扫两台模拟客户端的 `config`/`indexConfig`/`userdata`（跳过 `userdata\users` 凭据目录、`log`、`temp`），正则抽 `IP:port` 后并发 TCP 探活；绝不触碰 `D:\国金证券QMT交易端`）**：两台客户端配置里共出现 **26 个**去重服务端地址，仅 **4 个**可达 —— `180.169.107.19:56001`（登录，端口开而服务不应答）、`180.169.107.19:65000`（`g_update_url` 升级包下载 HTTP，与登录无关）、`81.69.152.51:59001` 与 `43.242.96.162:55300`（两个 proxy 通道）。其余 22 个全 FAIL：`175.25.41.66` 系列的 8 个端口（`indexConfig\xtconfig.xml`）、`175.25.41.69:55300/59500`（行情）、各家 `formulaserver` / `clientEnv` / `xtminiqmt` 地址。**关键结论：`g_xtservice_address` 与 `xtaddress.server` 都只有 `180.169.107.19:56001` 这一个值，客户端配置里根本不存在第二个登录节点地址** ⇒ 上面第 3 条「手工改写登录地址」不仅属未验证路径，而且**连可改的候选值都没有**，这条路彻底关闭。今后再遇到同样窗口，直接跑该脚本即可判断「是端口没起 / 是服务不应答 / 是否存在备用节点」，不必重新排查。

### 10.2 登录探针 `scripts/qmt_login_probe.py`（只读，唯一判定入口）

| 用法 | 说明 |
| --- | --- |
| `python scripts/qmt_login_probe.py` | 默认扫主号 + 沙箱，逐台打印结论 |
| `--client <目录> --json` | 指定客户端 / JSON 输出 |
| `--verdict` | 单行机器可读：`LOGGED=0/1 EXIT=n NODE=… TCP=0/1 STATE=…`（给脚本消费，绕开 PS 5.1 解 JSON 的编码坑） |
| `--date yyyyMMdd --as-of "yyyy-MM-dd HH:MM:SS"` | 回放历史某天日志（正/负样例回归用） |

- **护栏**：路径含 `国金证券QMT交易端` 直接 **rc=5** 并拒绝任何读取（交易版红线）。
- **日志解码**：QMT 引擎日志是**混合编码**（同一文件 UTF-8 与 GBK 行混着写），必须**逐行先 UTF-8、失败退 GBK**，整文件一次 decode 会出乱码。
- **判定优先级**（取时间最新的一类事件）：`login success` > `200003 超时` > `端口拒连`。`Proxy client not logged` **不参与排序**——它每 5 秒刷一条、永远是最新一行，会把真正的登录尝试结论盖掉；只在三类事件全缺席时才作"当日无登录尝试"兜底。
- **重启后旧成功要作废**：夜间闭环每轮都重启客户端，若 `login success` 的时间早于**本轮进程启动时间**，判为未登录（否则会把上一轮的登录态当成本轮的）。
- 退出码：`0` 已登录 / `2` 未登录（进程在） / `4` 进程不在 / `5` 触碰禁用目录。
- 已回归：10-28 16:19 → 已登录 rc=0（正样例）；10-28 23:59 → 端口拒连；10-29 00:3x → 200003 超时；交易版路径 → rc=5。

护栏（按顺序生效，任一命中就**什么都不做**）：停机开关 `data/schedules/qmt_retry_off` → 当日 PASS mark → 距上一份 **`deploy=PASS` 且 `dry_run=false`** 的报告 <4h 直接复用 → 时段闸 **08:50–15:10 不动**（绝不在盘中重启跑策略的客户端）→ **每日 ≤6 次尝试**（防登录抖动导致无限重启）→ 探针判未登录则只记 `WAIT` 不部署。补跑后还要求 **`latest.json` 是本轮调起之后才写出来的**（`LastWriteTime > 调起时刻`），否则闭环中途崩掉时会拿上一轮的旧报告冒充本轮结论。

> 未登录时**绝不做** build / 落盘 / 重启：那只会把客户端从"登录框"变成"登录框 + 新代码"，浪费一次重启并产生假 FAIL。
>
> 两层防重复：补跑调起的 `qmt_nightly_deploy.ps1` 现在**自己也带登录前置闸**（§9.5）。若探针判「已登录」后账号又掉线（券商侧抖动），闭环会整轮跳过、不写报告 ⇒ 补跑侧按「`latest.json` 不是本轮新写的」记 `SKIP`（不记 FAIL、不推「已登录但闭环 FAIL」这种会把排障方向带偏的卡），15 分钟后再试。

**收口提醒（2026-10-29 01:4x 加，补上一个观测盲区）**：`WAIT` 不推卡是对的（否则整夜每 15 分钟一张，共 44 张），但由此带来一个反向缺口——**券商维护一整夜时，从 21:30 到次日 08:45 一张卡都没有**，没人知道"这一晚到底跑没跑、为什么没有 PASS"，容易误以为脚本挂了或忘了。修法是在补跑窗口关闭前的**最后一次触发**推一张汇总卡（`warn`），内容含"本轮期零部署动作 ⇒ 没有 PASS 也没有 FAIL 报告"、最后一次探针原文、今晚会自动继续、以及"本地已无可修项 + 穷举无备用登录节点"的结论。去重靠 `data/schedules/qmt_retry_wakecard_<yyyyMMdd>.mark`，每日至多一张。

⚠️ **踩过的坑（差点写出反向 bug）**：窗口判定最初写成 `if ($hhmm -ge "0830")`。`$hhmm` 是 `"HHmm"` **字符串**，PowerShell 的 `-ge` 走字符串比较，于是 `"2130" -ge "0830"` 也为真 ⇒ 卡片会在**当晚 21:30 第一槽**就推出去（那时闭环才刚跑过一次 21:10 主任务，说什么"整夜未登录"都是错的）。补跑窗口跨零点，字符串比较必须**上下界都封住**：改成 `$hhmm -ge "0830" -and $hhmm -lt "0900"`。实测九点位（2130/2359/0015/0730/0815/0830/0845/0900/1030）只有 0830、0845 命中。
**通用规则**：任何 `"HHmm"` 字符串区间判断，只要区间**不跨零点**（如时段闸 0850–1510）单写上下界都安全；**跨零点或"取窗口尾部"**必须显式双向夹紧，或改用 `[int]` 数值比较。

**收口卡的结论句按探针签名分级（01:5x 加）**：原先无论 `EXIT=` 是几都写死"券商侧、本地已无可修项"，而 `EXIT=4` 的含义恰恰是**沙箱客户端进程没在跑**（本机/自启/安装完整性问题），把本机故障说成券商故障会把排障方向带偏一整天。现按 `qmt_login_probe.py --verdict` 的 `EXIT=` 分级：`2` → 券商侧 + 无备用节点（引 180.169.107.19:56001 穷举结论）；`4` → 本机，指路 `QMT_Sandbox_LogonStart/BootStart` 与 `initPythonEnv failed` 判据；`5` → 脚本被指向了非模拟目录（调用参数错误）；其余 → 只说"签名不明，读日志"。

### 10.3.1 分支矩阵回归 `_test_nightly_retry_branches.py`（16 例 / 37 项全 PASS，01:5x）

**为什么必须补这一层**：PASS 分支**从未真实执行过**——券商登录一直没恢复，线上每次走的都是 `WAIT`。也就是说"登录恢复的那一晚"恰好是这段代码的第一次实战，而它决定要不要落 mark、要不要推「已 PASS」卡、会不会白重启客户端。用测试把它提前跑一遍，比等到那一刻再发现问题划算得多。

### 10.5 01:00–01:16 自查修掉的四个真缺陷（无需拍板，均属本轮交付自身的质量问题）

**① 补跑任务的触发器是「一次性」的，只会在今晚生效。**
回读 `Get-ScheduledTask` 显示两条触发器的 `CimClass` 都是 `MSFT_TaskTimeTrigger`、`StartBoundary` 写死 2026-10-29，**没有 `ScheduleByDay`** ⇒ 10-30 起不再触发，「零介入守夜」实际只保一夜；且 `21:30+2h30m`（到 00:00）与 `00:45+8h` 之间还漏了 **00:00–00:45** 空窗。
现改为**单一每日触发器**：`-Daily -At 21:30` + `Repetition Interval=PT15M Duration=PT11H15M StopAtDurationEnd=true` ⇒ 每天 21:30→次日 08:45 每 15 分钟，无跨午夜空窗、永久循环。另加一条**一次性桥接触发器**（01:01 起 7h44m，到 08:45）把**今晚**剩下的窗口接上——因为每日窗口今晚要到 21:30 才开，直接替换会让 01:00–08:45 无人探测。桥接触发器到点自然失效，无需清理。
同时把 `MultipleInstances` 从 **Queue 改为 IgnoreNew**（一次闭环 build+部署+300s 轮询可接近 15 分钟，Queue 会让下一次探针对齐时叠跑、二次重启客户端），`ExecutionTimeLimit` 1h→2h。
修完实测：01:01:31 桥接触发器正常触发、`LastTaskResult=0`、走 `WAIT` 分支零副作用；回读 `MSFT_TaskDailyTrigger / 2026-10-29T21:30:00+08:00 / PT15M / PT11H15M / Interactive-Highest / IgnoreNew` 全部符合预期。修复脚本 `scripts/fix_qmt_nightly_retry_trigger.ps1`（可重复执行）。

**② `qmt_watch_login.ps1` 会和闭环的重启抢客户端，且判据是「TCP 通」这一轮刚被证明不可靠的信号。**
该守护每 10 分钟跑一次，逻辑是「56001 端口 TCP 可达 ⇒ 客户端没在跑就 `Start-Process reboot` 拉起」。两个问题：(a) 闭环中途本来就有几十秒的**无进程窗口**，守护抢在这里拉起 → 与闭环自己的重启撞车（正是 §9.3 bug① 的单实例交接 PID 抖动形态，足以把一次本来能 PASS 的补跑搞成假失败）；(b) 它的结论句 `停在登录框（需人工/验证码）` 就是本轮被推翻的那句误判来源。
修法（最小改动）：
- `qmt_nightly_deploy.ps1` 开头写 `data/schedules/qmt_deploy.lock`（含 PID/起始时间/模式），结尾删除；被强杀会留残锁，所以按**龄期 40 分钟**自动失效，不做后台清理。
- `qmt_watch_login.ps1` 在停机开关之后加**第 0 道闸**：锁新鲜 ⇒ 记 `SKIP 夜间闭环部署中` 直接退出，绝不碰客户端；锁过期 ⇒ 记 `STALE` 后照常工作。
- 该脚本第 3 步的结论改由 `scripts/qmt_login_probe.py --verdict` 给出（与 §10.2 同一判定入口），不再用 `Proxy client not logged` 正则猜；探针不可用时才退回日志兜底。

**③ PASS 判据取错了字段：`verdict=OK` 而不是 `deploy.result=PASS`。**
`qmt_nightly.py` 的 `verdict` 是三值 **OK / ATTENTION / FAIL**（来自两台客户端日志体检），部署成功但体检里出现非致命关注签名时是 `ATTENTION`，此时 `rc=0`、BUILD_TAG 已回读、部署确实成了。原补跑判据写的是 `verdict -eq "OK"` ⇒ 一轮"部署成功 + 体检 ATTENTION"会被判 FAIL，**白重启客户端直到烧完 6 次上限，并推一张假 FAIL 卡**。「部署成没成」的唯一事实是 BUILD_TAG 是否回读到期望值，与体检结论无关。
修法：补跑判据与「复用已有成功报告」护栏一律改看 `deploy.result -eq "PASS"`（且 `deploy.tag` 非空）；`verdict≠OK` 时 PASS 卡附加一句「总判定=ATTENTION，请读报告『客户端扫描』一节」，不再压掉成功。
验证：`_test_nightly_dryrun_guard.py`（本轮新增）+ 5 例分支表（真 FAIL→FAIL、PASS+OK→PASS、PASS+ATTENTION→PASS、期望 TAG 未回读→FAIL、只体检 `deploy=null`→FAIL 且不崩）。

**④ 演练（`-Rehearsal`）报告能冒充真实 PASS，把当晚的补跑永久压掉。**
01:08 为验证 ② 的锁生命周期跑了一次 `-Rehearsal`：`--deploy-dry-run` 只构建+校验、**不落盘不重启**，但 `qmt_autodeploy.py` 返回 rc=0 → `deploy.result="PASS"`、`tag=20261029-010836`，并且 `write_report()` 无差别覆盖 `latest.json`。若 ③ 修完就收工，15 分钟后的补跑会在「复用已有成功报告」护栏上直接落 `qmt_nightly_pass_20261029.mark` + 推「已 PASS」卡 —— **而沙箱其实一行新代码都没加载**。这是「演练能污染生产判定」的通用形态，不是本项目独有坑。
修法（三层，任一层单独都能挡住）：
- `qmt_nightly.py`：`deploy["dry_run"] = bool(no_restart or deploy_dry_run)` 落进报告 JSON；md 标题加 `[REHEARSAL 演练]`、结论区明确写「未落盘/未重启/未回读日志，**不算夜间闭环 PASS**，不参与补跑判定」。
- `write_report()`：演练报告**不写 `latest.json`**（latest 的语义＝最近一次真实闭环），文件名加 `REHEARSAL_` 前缀自我标注。
- `qmt_nightly_retry.ps1`：PASS 判据加 `-not $dryRun` 且**要求 `latest.json` 的 `LastWriteTime` 晚于本轮调起时刻**（`$fresh`）；「复用」护栏同样排除 `dry_run=true`，遇到演练报告记 `SKIP-REPORT` 后继续走补跑判定。FAIL 日志尾部带上 `报告本轮新写=/演练=` 两个布尔，便于事后定位是哪一层拦的。
- `qmt_nightly_deploy.ps1`：结论回显在演练模式改读最新的 `REHEARSAL_*.json` 并标 `[REHEARSAL 演练，不计 PASS]`，不再拿上一轮真实报告冒充本轮结论。
处置：手工把 `latest.json` 还原为 00:28 那份真实 FAIL 报告（`deploy=FAIL（未出 BUILD_TAG）`），演练两份文件改名 `REHEARSAL_20261029-010835.md/json` 隔离在 latest 链之外；确认当晚没有生成 mark。
验证：`_test_nightly_dryrun_guard.py` 11 项全 PASS（含「演练不覆盖 latest.json」「旧报告无 dry_run 字段时 `[bool]$null=False` 不误伤」）。**01:16:32 计划任务按新版脚本实跑**：日志 `WAIT 沙箱未登录…`、无 mark、无 attempts 计数、无部署动作，下一次 01:31:31 排队正常 —— 证明 ③④ 的改动没有把护栏改成「什么都不做」或「乱重启」。
