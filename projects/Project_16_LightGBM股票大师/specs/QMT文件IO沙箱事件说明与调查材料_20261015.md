# QMT Python 文件 IO 沙箱（Foribdden FileIO）事件说明与调查材料

- 日期：2026-10-15
- 撰写：QuantLab agent（op），基于客户端日志逐条取证
- 用途：向券商/迅投核查「nAuthValue 从 0 变 1」的原因与恢复条件
- 状态：**未解决——沙箱持续生效中，三个实盘策略（G2/ENS/V2）自 10-14 起无法交易**

---

## 一、一句话结论

**2026-10-13 晚 20:53~20:54，两台 QMT 客户端（同机不同安装目录、不同账号）在每日自重启登录时，服务端下发的 `setPyFileIOAccess nAuthValue` 从 0（放开）变为 1（限制），此后持续为 1。策略 Python 打开已存在文件一律抛 `PermissionError('Foribdden FileIO')`，导致文件桥类策略（G2/ENS/V2）读不到心跳/持仓/指令，连续两个交易日（10-14、10-15）换仓指令 100% 未执行。手动重启客户端（10-15 14:00）无效——重启后服务端仍下发 1。**

## 二、故障现象

### 2.1 策略侧报错（10-14、10-15 均有）

```
[P16G2][READ-JSON-ERR] D:/QMT_POOL/g2_bridge/cmd/orders_20261015.json: PermissionError('Foribdden FileIO',)
[P16G2][CMD-READ-FAIL] ... exists but read failed
[state] [!] 状态载入失败(build=20261014-150609): Foribdden FileIO
  File "<string>", line 829, in _load_state
  PermissionError: Foribdden FileIO
```

注意报错串拼写为 **`Foribdden`**（单 b 双 d），系 QMT 定制 `python36.dll` 内置字符串（非标准 Python 报错）。

### 2.2 沙箱行为特征（10-15 日志 30,327 行实证）

| 操作 | 结果 |
|---|---|
| `open()` 已存在的文件（读） | **拒绝**（PermissionError: Foribdden FileIO） |
| 新建文件 / tmp + `os.replace` 原子替换 | **正常**（写路径不受影响） |
| 枚举目录（os.listdir / exists 探测） | **正常** |
| 10-15 日志统计 | READ-JSON-ERR 共 **13,970 次，100% 为该报错**，无一例 FileNotFoundError |

### 2.3 业务影响

- **10-14**：G2 丢单（SELL 000607.SZ 200股 + BUY 000960.SZ 1100股未执行）；ENS 同样丢单（SELL 600691.SH 100股 + BUY 002762.SZ 2000股未执行）；V2 状态载入失败 → 全天空转零买入。
- **10-15**：G2 换仓指令（2 笔 SELL，09:54 写入）与 ENS 换仓指令（3 SELL + 1 BUY，10:08 写入）均未被消费；G2 策略在 14:00:56 重载后以 ≈330 次/秒硬撞 orders 文件，42 秒刷出 2.9MB 报错日志。
- 两日均**未发生错误下单**（读不到指令=不执行），但换仓全部错过。

## 三、根因取证：nAuthValue 开关

### 3.1 开关位置（每次交易登录完成时由客户端写日志）

```
[TC::CLoginManager::onInitTradeData] onInitTradeData getModuleAuthValue
[TC::CLoginManager::onInitTradeData] onInitTradeData setPyFileIOAccess nAuthValue : 1
```

- `nAuthValue = 0` → 文件 IO 放开（策略正常读写）
- `nAuthValue = 1` → 文件 IO 受限（沙箱生效，打开已存在文件被拒）

值由登录时服务端返回的 `moduleAuthValue` 决定（日志同时有 `[CProxyClient] receive module auth string : { "mdl_tradetype" : ... }` 行，为模块权限串）。

### 3.3 关键推论

1. **翻转时刻**：2026-10-13 晚 20:53~20:54（两台客户端每日自重启窗口，间隔约 40 秒先后登录）。
2. **两台同步翻转** → 几乎可排除单机本地因素（不是某一台的配置坏了），指向**服务端统一调整**（账户级/券商级/迅投服务端策略）。
3. **重启无效**：10-15 14:00/14:05 两台均完整重启并成功登录（日志可见完整登录流程：连接中→登录中→登录成功→加载配置），但登录后服务端**仍下发 nAuthValue=1** → 不是客户端进程态问题，是**服务端持久化授权**。
4. **本地无开关**：已检索两台客户端全部 `userdata/`、`config/` 下的 xml/ini/json（均 <5MB 全文匹配），**无任何文件包含 PyFileIO / FileIOAccess / nAuthValue 字段** → 本地无法配置或覆盖该值。

### 3.4 翻转原因（未定论，需服务端核实）

10-13 晚 20:53 翻转本身发生在服务端，本地日志只能证明「客户端请求登录，服务端返回 1」。可能方向（均未经证实）：

- 券商侧对账户的 QMT 模块权限做了调整（如 Python 策略文件 IO 权限收紧）；
- 迅投服务端策略调整（如对模拟环境统一开启限制）；
- 账户权限串（module auth string）中某模块标志变化（日志有 `receive module auth string`，可对照翻转前后内容差异，但需服务端字段定义）。

## 四、已采取的处置（供参考，均已落地）

1. **防重复建仓**：10-15 的两份 stale 指令文件已归档（重命名 `_done_1`），即使沙箱解除也不会消费过期指令。
2. **策略侧防护（10-15 新 build）**：G2/ENS/V2 三策略均已加「IO 预检 + 转被动」逻辑——沙箱生效时策略自动转被动（不读指令、不下单、只写心跳），防止「读不到状态 → 持仓=0 → 盲跑重复买入」。当前策略状态：**安全但停摆**。
3. **漏单处置**：10-14/10-15 漏掉的换仓指令不人工补单，待沙箱解除后由次日日度管道重新推导。
