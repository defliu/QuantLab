# QMT 文件 IO 沙箱（Foribdden FileIO）根因定论与解决方案

- 日期：2026-10-15
- 撰写：QuantLab agent（op）— 全网检索 + 客户端日志字段级取证
- 配套材料：`QMT文件IO沙箱事件说明与调查材料_20261015.md`（事件时间线，本文为其根因定论 + 解法）
- 状态：**根因已定论（字段级铁证）**；恢复仍需券商侧动作

---

## 一、结论前置

**这不是 bug，不是本地环境问题，也不是客户端升级导致的。**

**根因**：券商/迅投服务端在 **2026-10-13 20:53~20:54** 将账户的**两项策略 Python 权限**从「放开」翻转为「限制」：

| 权限字段 | 含义 | 10-13 晨间 | 10-13 晚间起 |
|---|---|---|---|
| `m_nPythonOpFile` | 策略 Python 允许操作本地文件 | **0（放开）** | **1（限制）** |
| `m_nPythonConnectNet` | 策略 Python 允许外部网络连接 | **0（放开）** | **1（限制）** |

`setPyFileIOAccess nAuthValue` 就是 `m_nPythonOpFile` 的下发值；报错 `PermissionError('Foribdden FileIO')`（QMT 定制 python36.dll 拼写 Foribdden）即该权限位为 1 时的硬拦截。

**全网检索已找到对应事件**：券商 2026-10-08 推送《[重要]内置 Python 策略功能调整》通知，**预计 10 月 23 日完成升级**，明确关闭内置策略文件读写 + 外部网络连接。10-13 晚的翻转是这次升级的**灰度提前生效**。

**恢复路径**：账户级服务端授权，无法本地绕过。需通过**券商客户经理/客服**申请恢复 `m_nPythonOpFile`。

## 二、本地取证：字段级铁证

### 2.1 证据一：整个权限结构中，只有 2 个字段翻转

对 10-13 同一天两次登录（晨间 08:52 = 放开 / 晚间 20:53 = 限制）的 `user permission` 结构做逐字段 diff，**130+ 字段中仅 2 处不同**：

```
62,63c62,63
< m_nPythonConnectNet: 0
< m_nPythonOpFile: 0
---
> m_nPythonConnectNet: 1
> m_nPythonOpFile: 1
```

其余全部一字未变（含 `m_nStockProgrammaticTrade`、`m_nRevokeOrder`、`autoexecution`、`m_nQuickOrder` 等交易类权限）。这排除了「账户被整体降权」，精确定位为**两个 Python IO 权限位被单独收紧**。

### 2.2 证据二：module auth string 1303 字段逐字段完全一致

`receive module auth string`（模块权限串）在晨间与晚间**逐字段 diff 无任何差异**（均 1303 字段）。这**推翻了**原调查材料 §3.4 猜测的「账户权限串中某模块标志变化」——权限串没变，权限位变了。真正的载体是 `user permission` 里的 `m_nPython*` 两个字段。

### 2.3 证据三：客户端版本全程未变，排除自动升级

10-12 / 10-13 / 10-14 / 10-15 四天日志 `VERSION INFO` 全部为 `version 2.1.19.0 / Revision 654567 / Build 2026-06-18 16:17:32`。**10-13 晚那次翻转不是「自动升级导致新版本默认开启」**，是服务端在同一版本上直接改了账户授权。

### 2.4 两台客户端同步性（交叉验证）

| 客户端 | 10-13 08:52 | 10-13 20:53/54 | 10-15 手动重启后 |
|---|---|---|---|
| A `D:/QMT交易端模拟`（70180771） | OpFile=0, Net=0 | OpFile=1, Net=1 | — |
| B `D:/国金QMT交易端模拟`（67014907） | OpFile=0, Net=0 | OpFile=1, Net=1 | OpFile=1, Net=1 |

两台**同一客户、同一机器、不同安装目录、不同账号**，在 40 秒内先后翻转，且字段完全一致 → 指向**账户/客户级服务端统一策略**，而非单机因素。原材料「排除单机本地因素」的判断成立。

## 三、全网检索：原因定性

### 3.1 直接对应事件（券商推送）

**《[重要]内置 Python 策略功能调整》券商通知**（2026-10-08 推送，2026-10-09 流出，**预计 10-23 完成升级**），三条核心内容：

1. **关闭内置 Python 策略文件读写功能**——「涉及本地文件读写的功能（包括但不限于 open()、read()、write() 及相关第三方库）均无法使用」；
2. **关闭内置 Python 策略外部网络连接**——HTTP/TCP/UDP、MySQL/Redis/SQLite、局域网通信全禁；
3. 取消登录页独立交易（miniQMT）选项。

通知末尾划定安全区：**「使用内置 python，且不与外部进行任何交互的策略不受上述调整影响」**。

### 3.2 监管背景

券商收紧的根因是**穿透式监管 / 程序化交易新规**：策略逻辑、服务器部署须报备，策略与外部信号通道被视为「黑盒监管盲区」。多家券商（国投、东财、国金、江海等）自 2026 年 8-9 月起陆续对 miniQMT 外接、文件单、ACT 系统 python 文件/网络权限进行「筛选与收回」。这套「文件桥（G2/ENS/V2）」正是被清撤的典型形态。

### 3.3 与原材料的咬合

- 原材料时间线（10-13 20:53 翻转、两台同步、重启无效）与「10-08 通知 / 10-23 升级」完全咬合 → 翻转是这次统一升级的**灰度提前生效**，比官方 10-23 早了 10 天。
- 原材料「Foribdden FileIO 来自 QMT 内置 python36.dll」→ 对应定制解释器对 `m_nPythonOpFile=1` 的硬拦截。

## 四、影响面：还有一个尚未爆的雷

除了已观察到的「读文件被拒」，翻转同时打开了 **`m_nPythonConnectNet=1`（网络限制）**：

- 三条腿里**任何依赖策略侧发起网络连接的逻辑都会失效**（G2/ENS 目前靠文件桥，但若代码里有任何 HTTP/socket/数据库调用，现在也在被拦）；
- 券商通知明确点名 **SQLite 被双重封堵**（既是文件也是数据库连接），**不要指望用 SQLite 替代 JSON 文件**。

**建议**：对策略代码做一次全局危险调用扫描（`open(`、`os.replace`、`pathlib`、`sqlite3`、`requests`、`socket`、`pymysql`……），确认除文件桥外无其他外部交互。

## 五、恢复方案（按优先级）

### 方案 A：找券商申请恢复（唯一根治，推荐）
联系客户经理/国金客服，说明：账户 QMT 内置策略的「文件读写权限（m_nPythonOpFile）」被收紧，影响既有自动化策略，请协助恢复或申请白名单。依据：

- 券商 10-08 通知本身留了口子：「使用内置 python 且不与外部交互的策略不受影响」——本策略属自营闭环，可据此申请豁免；
- 部分券商在升级后给「白名单方案」，值得一问。

**时效**：官方统一升级 10-23 完成，越晚越难单独恢复。建议今明两天就联系。

### 方案 B：改造策略，去掉文件桥（长期必做，不依赖券商）
无论券商是否恢复，新规方向明确。文件桥类架构需改为「策略内自闭环」：

- **状态存内存/全局变量**：用 `ContextInfo` 属性保存持仓与状态，重启后从 `get_trade_detail_data` / 账户持仓重建；
- **信号来源内化**：把「外部管道写文件 → 策略读文件」改为「策略自己算」或「用 QMT 内置接口取数」；
- **禁 SQLite**：已被点名，不要当替代。

**代价**：架构级改造，G2/ENS/V2 三条腿都要动，工作量大。**但这是唯一不依赖券商的路径，建议与方案 A 并行启动**（先让 DE 出一版改造方案 + 工作量评估）。

### 方案 C：临时绕过（不可靠，不推荐）
全网有零星案例称「找客户经理确认，或把文件放到 D 盘/E 盘特定路径」可绕过（2026-09-02 一篇 QMT 实战文章提到换盘符路径）。**但**这基于旧版行为，与本次服务端字段级收紧性质不同，大概率无效。仅在券商答复「按目录授权」时才值得一试。
