## 一、为什么改（背景，30 秒读完）

2026-09-28 我们给 `rebalance_daily.py` 加了候选审计溯源：live 运行后 plan json（`data/rebalance_<date>.json`）会带 7 个候选溯源字段（`candidate_file / candidate_loader / candidate_data_date / candidate_rows / candidate_rows_raw / candidate_sha256 / candidate_asof`），并在读取候选时把原始字节快照落 `data/candidates_asof/` 只读留档。这是「当天到底读到了什么候选」的唯一审计链。

**2026-09-29 实测发现 09:45 任务会亲手写这个文件**：

- 当日时序（红线空仓日）：~10:02 脚本跑过（asof 留档落地 ✓，但红线空仓在写 plan json **之前**早退，当日脚本不产 json——已知行为）→ 10:05 Windows guard 兜底重跑（同样早退）→ **10:10:05 你的会话收尾仍按 prompt 指令把 `rebalance_20260929.json` 写出来**。
- 铁证：该 json 含 `live_invoked`、`positions_at_run`、`f2_primary_source` 等键——**全项目没有任何脚本会写这些键**（grep 实证），只能是 agent 手写；且不含 `candidate_sha256` 等 7 个溯源字段。
- 根因就是现行 prompt 的 step 4 第一句「**保存换仓结果到 data/rebalance_<date>.md/.json**」——它指示 agent 去写这个文件。09-29 恰逢脚本没写 json 所以"没有覆写对象"，但**正常交易日脚本会先写好带 7 字段的 plan json，同一行为就是把它整个覆写掉**——审计链（候选溯源 7 字段）当场丢失。

这个 json 还有第二个身份：**10:05 Windows 兜底任务（`rebalance_daily_guard.ps1`）的幂等标记**（读它的 `executed_live` 判断 09:45 是否已执行）。agent 改写它 = 同时在动兜底任务的判断依据。
