## 一、机制设计验证：设计意图确实正确

### 1.1 设计意图（代码注释原文）

`projects/Project_16_LightGBM股票大师/g2_candidates_night.ps1`：

```
# 每日 20:05 预生成次日 G2 候选（T-1 数据已就绪：16:30 面板增量 + 19:30 Tushare moneyflow 刷新）
# 根因：deploy_predict_g2 无 --date 时按快照最新日（=运行日）命名候选文件，
#      20:05 夜间产物实际是"次日候选"但文件名是运行日
#      → 次日早晨 rebalance 新鲜度闸必拒，周五→周一断链尤甚
# 修复：按 is_trade_day.py 日历推下一交易日，复制当日产物并改写 trade_date 列为下交易日，
#      生成 <下交易日>_g2_top{10,3}.csv（周五 → 周一可用）
```

**设计意图 = 用「T 日收盘后的完整行情」生成候选，供 T+1 早盘换仓使用。这是正确的、无前视的实现。**

## 二、r1「交集为零」的真正成因：副本被次日正品覆盖

### 2.1 副本生命周期（核心发现）

```
T 日 20:05  夜跑 deploy_predict_g2
            → 产出 <T>_g2_top10.csv / <T>_g2_top3.csv（当日正品）
T 日 20:08  生成副本 <T+1>_g2_top10.csv（内容=T 日数据，trade_date 改写为 T+1）
                                    ↓ 副本此刻有效
T+1 日 09:5x  rebalance 读 <T+1>_g2_top10.csv
            → 读到的正是副本（内容 = T 日收盘行情）✓ 完全符合设计
T+1 日 20:05 夜跑 deploy_predict_g2
            → 快照最新日 = T+1 → 直接覆写 <T+1>_g2_top10.csv（正品覆盖副本）
                                    ↓ 副本消失，不可追溯
```

### 2.2 实测证据：`20260916_g2_top10.csv` 被覆盖

| 时间 | 事件 | 文件内容 |
|---|---|---|
| 09-15 20:08 | 生成副本（来自 09-15 数据日） | 内容 = 09-15 数据日候选 |
| **09-16 20:07** | **次日正品覆写（mtime 变化）** | **内容 = 09-16 数据日候选** |

实测该文件当前内容：
```
688636.SH, 60.5, trade_date=20260916
920981.BJ, 60.5, trade_date=20260916
```
→ **已是 09-16 正品，09-15 的副本内容已不可考。**

### 2.3 r1 的审计失真从何而来

r1 拿 `rebalance_YYYYMMDD.json` 的 target 比对 `YYYYMMDD_g2_top3.csv`，**16/16 交集为空**——
因为事后读到的 `YYYYMMDD_g2_top3.csv` **已被当日正品覆盖**，而当时换仓实际读到的是**副本**。

```
事件顺序：
  09-22 20:08  生成副本 20260923_g2_top3.csv（内容=09-22数据日）
  09-23 09:5x  换仓读 20260923_g2_top3.csv → 读副本 ✓
  09-23 20:05  正品覆写 20260923_g2_top3.csv → 副本消失

  r1 事后比对时读 20260923_g2_top3.csv = 09-23 正品（≠换仓时读到的副本）
  → 交集为零 = 审计假象，非执行错误
```

**关键证据**：`20260922_g2_top3.csv` 的 mtime 是 `2026-09-22 20:08`（**当日夜生成即被正品路径占用**），
而非次日；说明该文件名空间被「副本」与「正品」**共用**。

## 三、真实缺陷（r2 新增定位）

### 🔴 缺陷 A：副本与正品同路径同命名 → 覆盖 → 事后不可审计

- 副本 `dst = ${nextDay}_g2_${n}.csv`
- 次日正品 `deploy_predict_g2` 按快照最新日命名 = `${nextDay}_g2_${n}.csv`
- **两者路径完全相同** → 正品覆盖副本
- 后果：
  1. **任何事后审计都无法复现实盘当时的输入**（本次 r1 误判即由此产生）
  2. `compare_g2_daily.py` 盘后复跑对比机制的可复现性受影响
  3. 出现异常时无法追溯「当时到底读了什么」

**建议**：副本改用独立目录或加后缀（如 `_next`），或落档运行日志时记录候选文件内容哈希。

### 🔴 缺陷 B：`rebalance` 执行记录无候选溯源字段

`data/rebalance_YYYYMMDD.json` 只有 `target`，**没有记录实际加载的候选文件路径、数据日、内容哈希**。
这是 r1 必须靠三方对拍（而非直接读日志）才能定位的根本原因。

**建议**：新增 `candidate_file` / `candidate_data_date` / `candidate_hash` 字段。

### 🟡 缺陷 C：`source 定位` 修复曾未生效（09-25 需人工兜底）

```
[20:09:15] 下一交易日=20260928（运行日=20260925），生成次日候选副本
[20:09:15] [INFO] 当日 20260925_g2_top10.csv 不存在（红线无候选属设计内宁缺毋滥），跳过次日副本
[20:22:59] [MANUAL] opencode 手工补生成次日候选 20260928（源=20260924 修复版产物）：
           脚本按运行日(20260925)找源、假时 target=20260924 错位致自动复制跳过；ps1 根因待拍板
```

根因：`$runDay=20260925`，但产物按 `$targetDay=20260924` 命名 → 找源 miss。
**该问题已于 2026-09-26 拍板修复**（改为读快照 `trade_date.max()` 作 `$targetDay`），
但 09-25 当晚仍需人工干预，且日志留有 **`ps1 根因待拍板`** 字样，**修复后的自动路径尚待下个周五实测**。

## 五、那「背离」到底还存在吗？

**r1 的「口径错位导致背离」解释已作废。** 剩余的背离可能成因收窄为：

| 候选成因 | 状态 |
|---|---|
| ~~时间口径错位~~ | ❌ 已排除（机制正确） |
| rank 非单调 + 实盘只买 TOP3 | ⚠️ 存疑，但需重算——纸面「TOP3(实盘口径)」统计的是**运行日候选**的 rank1-3，而实盘买的是**副本（前一数据日）**的 rank1-3，**两者仍是不同票集** |
| 实盘样本量过小（仅 22 笔 / 8 个成交日） | ✅ 成立，统计功效不足 |
| 实盘桥账本口径 vs 纸面口径差异 | ⚠️ 未验证 |

**因此：背离现象（纸面 +2.9% vs 实盘 -4.0%）依然存在且成立，但 r1 给出的成因是错的。**
真正的成因仍需在「纸面统计应改用副本内容重算」之后才能定论——**这是下一步该做的事**。
