## 四、核心算法要求

### 4.1 复权口径（错则全盘皆错）
`adj_factor` 是后复权因子。前复权价 = `close * (adj_factor / 最新 adj_factor)`。
计算 N 日累计涨幅时，**分母分子必须用同一基准的复权价序列**，否则除权日炸出假跳空。
实现提示：对每只股票按日期升序取 `close`、`adj_factor`，
用 `close * adj_factor` 作为价差约等序列（后复权价的单调等价变换）亦可，
但必须在代码注释里写明你选了哪种口径及理由。

### 4.2 PIT 股票池（防幸存者偏差）
构造某交易日 T 的可交易池，**只能用 T 当日及之前可得的信息**：
- 当日有行情记录（`trade_date == T`）
- `is_st` 不为真
- `listed_days >= 252`（用当日该字段值，不要用全表最新值）
- `amount`（成交额）达到门槛
- `circ_mv` 在区间内（单位注意：`circ_mv` 是**万元**，30亿 = 300000）
**严禁**用"今天的成分股名单"回算历史排名。

### 4.3 RPS 计算
对 window in (20, 60, 120) 三个窗口各算一次：
- 个股 window 日累计涨幅 `ret_w`
- **当日横截面百分位**：`rps_w = pct_rank(ret_w)`，映射到 0-100，最强 100
- 用 `scipy.stats.rankdata` 或 `df.rank(pct=True)` 实现，注意并列取平均

### 4.4 历史状态快照（这层不能省）
「首次入榜日」「排名变化」「入榜以来收益」必须有历史记忆，单日 CSV 算不出来。
落盘两个文件：
- `results/rps_rank_daily_<YYYYMMDD>.csv`：当日全池排名明细
- `results/rps_state.parquet`：滚动状态，键为 `ts_code`，每跑一天**更新**该文件

状态字段至少包含：
`ts_code, first_top20_date, first_top50_date, last_rank_20, prev_rank_20,
rank_chg_20, ret_since_top20, max_ret_since_top20, in_top50_now,
consec_days_in_top50, last_update_date`

其中"入榜以来收益/最大涨幅"用**自首次入榜日收盘价至今收盘价**的涨幅计算，
需在状态里保留入榜日收盘价作为锚。

### 4.5 质量门控（失败必须非零退出，不许静默出一份"正常日报"）
独立函数 `quality_gate()`，检查项：
1. `trade_date` 是否为预期交易日（与 stock_daily 最大日期一致）
2. 当日覆盖股票数 / 预期池大小，比值不得低于配置阈值
3. `rps_20` 是否存在缺失值
4. 排名唯一性：同窗口内 `rps` 取值不得大量重复（检查 unique 比例）
5. 若启用涨停池/题材：当日该接口返回条数
任一项不过 → 打印 `[GATE-FAIL]` 明细 + `sys.exit(1)`。

### A.1 【致命坑】`pq.read_table(..., filters=...)` 会把过滤列提升为 DataFrame 索引

本机环境为 pyarrow 25.0.1 + pandas 3.0.5，该组合下：

```python
t = pq.read_table(SRC, columns=[...,"trade_date","ts_code",...],
                  filters=[("trade_date",">=",pd.Timestamp(...))])
df = t.to_pandas()
# df.columns -> ['close', 'amount', ...]   trade_date / ts_code 不在列里！
# df.index   -> MultiIndex(['trade_date', 'ts_code'])
```

即**凡出现在 `filters` 里的列，`to_pandas()` 后会被移到 index 而不再是普通列**。
后续任何 `df["ts_code"]` 都会抛 `KeyError: 'ts_code'`，而 RPS 计算必须按 `ts_code`
分组取时间序列，此坑必踩。

**正确写法（二选一，推荐第一种）**：

```python
# 方案 1：显式 reset_index 还原为普通列
df = pq.read_table(SRC, columns=cols,
                   filters=[("trade_date", ">=", pd.Timestamp(last))]).to_pandas()
if isinstance(df.index, pd.MultiIndex):
    df = df.reset_index()

# 方案 2：完全不用 filters，先读日期索引列再自行切片
```

**硬要求**：`ts_code` 与 `trade_date` 在进入任何 groupby/pivot 之前，
必须是 DataFrame 的**普通列**。请在读数后加断言，例如
`assert "ts_code" in df.columns and "trade_date" in df.columns`。

#### 飞书推送（2026-10-04 业主拍板追加）

业主要求「成功和失败都推，不然我知道结果」。收件人**复用 Project_16 的
`FEISHU_OPEN_ID`**（`ou_bd13...3eeff`），P22 自身不另设收件人配置。

**收件人取值方式**：包装脚本在运行时用正则从 `P16/qmt_config.py` 的
`FEISHU_OPEN_ID` **动态提取**，**P22 侧不留任何副本常量（已移除同值 fallback）**。
解析失败时**fail-closed：不推送**，正文留档到
`results/logs/push_failed_<tag>_<时间戳>.txt`，退出码 `2`。

**为什么不用同值 fallback 兜底**：副本一旦存在，P16 换人后 P22 会静默推给旧
open_id——业主以为在收通知、实际无人收到，这是**无声失联**；而「推不出去」
有 `exit 2` + 留档可查、可修。两者相比，「推错人」危险得多，故选 fail-closed。

| 场景 | 是否推送 | 内容 |
|---|---|---|
| 交易日成功 | **推** | Top10 代码 + RPS20/60/120 + 涨停标记 + 题材 |
| 成功但摘要构建异常 | **推** | 降级为基础通知（日期 + 池规模 + 产物路径），仍满足「成功必推」 |
| 日历探测故障 | **推** | 异常信息 + 探测输出 |
| 探测无 `HIT=` 标记 | **推** | 判为故障而非非交易日 + 原始输出 |
| `rps_daily.py` 运行失败 | **推** | 日期 + 退出码 + 日志路径 + 末尾 25 行 |
| 退出码 0 但产物缺失 | **推** | 两份产物各自存在性 |
| 非交易日跳过 | **不推** | 设计如此：只在真有结果时告知，避免长假刷屏 |

- **推送出口**：以 **CLI 方式**调用 `projects/Project_16_LightGBM股票大师/lark_push.py`
  （`--file ... --user-id ... --title ...`），**不跨项目 import**——该模块的
  `record_failure()` 把兜底记录写死在 `_proj_dir()/data/schedules/`（即 P16 目录），
  import 会让 P22 的失败记录落进 P16 账下、归属错乱。
- **P22 侧自留失败留档**：CLI 方式下P16 的兜底记录仍会落在 P16 目录（跨项目查不到
  等于没留痕），因此推送失败时包装脚本把未送达正文改名为
  `results/logs/push_failed_<tag>_<时间戳>.txt` 并附推送返回与收件人；
  成功才删除临时 `msg_<tag>.txt`。
- **`--file` 而非 `--text`**：避开 Windows 命令行 32767 字符上限。
- **推送是「非核心动作」**：推送失败**不改变产物判定**，仅以 `exit 2` 标记
  （兑现下方退出码表中此前只有契约、无实现的 `2`）。
- **实测**：成功分支与失败分支均已实跑，`lark_push` 返回 `"ok": true` 且返回
  `message_id`（真实送达，非仅「调用成功」）；通知降级分支（核心成功 + 推送失败）
  亦已实跑，退出码 `2` 符合契约。

#### 交易日判定必须两层，缺一不可

| 层 | 手段 | 作用 | 若缺失的后果 |
|---|---|---|---|
| 第1 层 | 触发器 `DaysOfWeek=62` | 挡掉周末 | 周末白跑 |
| 第 2 层 | 脚本内查 `stock_daily` 主库当日是否已有行情 | 挡掉法定节假日/调休/主库未更新 | **春节国庆全被误触发**，产出一堆空跑 |

**第 2 层为什么查主库而不是查 Tushare 交易日历**：与 `rps_daily.py` 自身的日历判断
同源（同一 `stock_daily` 日历），避免两套判断互相打架；且主库「当日有无数据」
本身就是「收盘且已更新」的真实信号，比纸面日历更贴合实际可产出状态。

#### 退出码契约（与既有任务不同，勿误读）

| 码 | 含义 | 是否异常 |
|---|---|---|
| 0 | 已产出且推送成功 / 非交易日正常跳过 | 否 |
| 1 | 交易日运行失败（门控 FAIL 或产物缺失）**或日历探测故障** | **是**，需人工介入 |
| 2 | **通知降级**：产物已落盘且核心计算成功，但飞书推送失败 | 否（但表示业主收不到通知，需人工确认） |

`exit 2` 已于2026-10-04 落地实现（此前只有契约、无实现）：成功路径末尾不再是
无条件 `exit 0`，而是捕获推送返回值——推送失败即`exit 2`，
避免「跑成功但没推送到」在任务调度器里与完全正常无法区分（静默失联）。
实测：核心成功（daily 50 行）+ 推送失败 → 退出码 `2`，且 P22 侧生成
`results/logs/push_failed_<tag>_<时间戳>.txt` 留档未送达内容。

**注意：非交易日返回 0 是设计，不是「静默失败」**——排查时必须看
`results/logs/rps_daily_run.log` 的「交易日判定」行与 `rps_daily_YYYYMMDD.log` 是否生成，
不能只看退出码。

**探测故障必须返回 1 而非 0（fail-closed，2026-10-04 收尾修订）**：日历探测本身
失败（Python 异常、主库 parquet 不可读、输出无 `HIT=` 标记）时无法区分「非交易日」
与「基础设施故障」，早期实现按fail-safe 返回 0，等于把故障静默吞成正常跳过。
现已改为 exit 1，并新增「输出无 `HIT=` 标记即判故障」的显式检查。
