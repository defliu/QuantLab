## 三、op 5 项修复逐条裁决

### Fix 1：让 `_retry_pending` 收敛（核心）——**正确，但需一个关键约束**

「无 id 也计数（retries+1、重置 time），达 3 次由调用方回滚」的方向正确：当前 pending 唯一的日内出口是 14:50 对账，交易时段内 10 只单空转 3.5 小时、账本虚扣现金 4 万+，必须收敛。

**关键约束（op 提问的答案）：「计数后继续走撤单+重下」有双成交风险，「无 id 即立刻回滚」过于激进。安全的收敛路径是第三种——计数但绝不重下：**

- **为什么不能「计数+照常重下」**：`_retry_pending` 的重下（L473/475）发生在撤单之后；若撤单没成功（模拟端撤单能力本身存疑，见 §四），旧单还活着，重下 = 同票同方向两笔 live 单，双双成交 = 双倍建仓。当日 000570 等票的「双实例重复下单」就是这个形态的实证预演。
- **为什么不必「无 id 立刻回滚」**：14 只进入空转的票里有 4 只（002054/300407/300636/603585）在数分钟~数十分钟内自然成交。立刻回滚会放弃这些自然成交机会；回滚本身要撤活单（`_rollback_pending` L417-422），撤不动时账本回滚而活单仍在，状态反而更绕。计数+等待（3 分钟×3 次 ≈ 9-12 分钟）保留了「再等等」的窗口，同时保证有界收敛。
- **推荐形态**（`_retry_pending` L466-469 改造）：

```python
if order_id is None:
    # 反查不到可撤 id：计数收敛，但绝不重下（旧单可能仍活着，重下=双成交）
    info["retries"] = info.get("retries", 0) + 1
    info["time"] = _get_market_time(C)   # 重置超时，给自然成交留窗口
    _pending_orders[code] = info
    _log("[pending] %s 未反查到可撤订单，不重下仅计数 retry=%d/%d" % (code, info["retries"], PENDING_MAX_RETRIES), C)
    return
```

配合 L542 的 `retries>=PENDING_MAX_RETRIES → _rollback_pending` 原有逻辑（回滚内部先 best-effort 撤活单），即得完整收敛链：**空转→计数→回滚→14:50 对账校准**，全程无重复下单窗口。

**裁决：正确（needs-adjustment 级微调）——「计数」对，「照常重下」必须显式禁止。**

### Fix 5：官方撤单 + 撤单确认——**方向正确，是全方案的关键路径，但模拟端可用性未证实，必须先探针后上线**

- **`_cancel_order_by` 确认是错的**：三重证据链——①调研 §4.1：passorder opType 枚举无撤单值，24=股票卖出；②踩坑案例集 §3.2：用户亲见界面「显示卖出不是撤单」；③P16 L286-288：模拟端实测 passorder(24) 把 order_id 当价格解析、报「下单数量为0」。调研同时留了一句公道话（「不要直接删，万一它在本环境确实生效，先对照实验」）——但 V2 当日撤单 0 次，该写法在本环境**连一次成功记录都没有**，无保留价值。
- **官方 `cancel()`/`can_cancel_order()` 在国金模拟端是否可用——这是 op 最需要的结论，诚实回答：只读证据不足以证实，也不能证伪。** 证据两面：
  - 支持：踩坑案例集 §3.2 给出无条件正确姿势（`cancel(orderId, acct, 'stock', C)` + `can_cancel_order` 预检 + `orderId=m_strOrderSysID`）；P16 v13（同账号 67014907、同一模拟端）生产代码用的就是这套（`_cancel_order_by_id` L642-662），且其 `_handle_timeout_retry`/`_handle_cancel_confirm`（L749-896）实现了完整的「撤单→轮询确认终态→死透才重报→未确认延后复查」纪律；
  - 存疑：P16 `_extract_order_id` 旧注释写「模拟端撤单只能走 QMT 界面手动」（针对 passorder(24) 路线，但未明确官方 cancel() 在模拟端的实测结果）；我的可读文件里没有任何一条模拟端 `cancel()` 成功的运行日志。
  - **结论：按「文档正确、实测未证」处理——先探针，后上线（见 §五 探针实验）。**
- **撤单确认超时怎么办**：照抄 P16 纪律（这是它用真金白银换来的）：撤单指令发出后短轮询确认订单进入终态（53 部撤/54 已撤/56 全成/57 废单；**55 部成是活跃态**，调研 §2.3/§4.2、P16 L44-45 三处一致）；**未确认死透绝不重下**，保留 pending 延后复查（P16 L803-807：`info["time"] = now - PENDING_TIMEOUT + 60` 延后 60s，不重报不计数）；撤单重发上限 2 次（P16 L885-889 `cancel_retry`）；最终仍死不透 → 放弃重下、走回滚/对账。**绝不允许「撤单超时→当已撤→重下」的乐观路径。**
- 注意参数类型：踩坑案例集 §3.4（`[CANCEL-ERR] order_id=2882: Python argument types`）——`cancel()`/`can_cancel_order()` 的 orderId 类型要求未实测，探针实验里要一并验证 str/int 两种传法。

**裁决：正确（含撤单确认环节），但整条 Fix 5 必须以「模拟端 cancel() 探针实验通过」为上线前置条件；确认超时的处置按 P16 纪律（延后复查、绝不乐观重下）。**
