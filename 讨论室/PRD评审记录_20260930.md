## 9. 评审意见（op，2026-09-30）

> **定位判断先行**：本文档是一份「通用量化平台」PRD，但未声明与既有 QuantLab 资产的关系。本评审按两种可能定位分别标注：[存量复用] = 应引用/改造本仓库已有实现；[新平台] = 若确为独立新建，需说明新建理由与迁移边界。

### 9.1 总评

骨架合格，可作为排期讨论起点；但按本仓库 2026 年的实证与实盘教训，当前版本**不足以直接作为排期与验收依据**。四大主因：验收标准不可比、回测引擎自身验证体系缺失、QMT 生产硬约束全缺、7 类策略无优先级（未消化本仓库已有证伪结论）。建议修订出 v1.1 再进排期。

### 9.2 优点（v1.1 保留，勿改）

- L1–L8 分层与 L3/L6 解耦（策略只输出 `TargetPortfolio`，不下单）方向正确。
- §0 三条关键约束（禁硬编码标的/仓位、回测实盘同一套信号代码、样本外+成本敏感双门槛）是防"回测作弊"的底线，正确。
- 数据层点名幸存者偏差、复权方式记录、质量报表；成本模型含参与率冲击项 `k*(V/barV)^γ`；§8 Gate 含参数扰动 ±20%、成本×2——均为合格 PRD 应有项。

### 10.2 §9 未覆盖的缺口（新增）

#### P0 级（我判为不补不能进排期）

**N-P0-1 全篇无非功能需求（NFR）——这是 §9 漏掉的最大结构性缺口。**
文档定义了 8 层能力，却没有任何性能/容量/存储/资源预算。而数据体量是已知且很大的：`daily/stock_daily.parquet` 覆盖 2009-01-05 ~ 2026-08-21、**1457 万行 × 33 列**，分钟线 **5 个周期 × 5826 只**，财务 8 张表。更关键的是 §4/§8 引入的**回测次数乘数**：7 类策略 × 参数扫描 × ±20% 扰动 × 成本×2 重跑——没有单次回测耗时预算，排期根本无从估算。
**建议 §NFR 明确**：①单策略 10 年日频全池回测 ≤ X 分钟；②参数扫描总机时预算；③峰值内存；④分钟/Tick 数据冷热分层与存储上限；⑤部署假设（本机单机 vs 服务器）。
**理由**：个人投资者单机运行，"能不能在盘前跑完"直接决定架构——是否需要预计算缓存、是否需要列存、是否需要把分钟级回测降级为抽样。

**N-P0-2 只有"上线 Gate"，没有"退役判据"与实盘-回测偏离监控。**
§8 六条全是 entry gate；实盘跑起来后"何时降仓/停机/退役"完全未定义。而本仓库恰恰是**事后**才判死了一批策略：P11 ETF 轮动 7.6 年跑输基准、P12 RPS 全周期 -60.8%、P21 日内做 T 0/6 族过线。没有退役机制的"平台"只会上线不会下线，长期必然积累僵尸策略、白占额度。
**建议**：①滚动窗口表现门限（如滚动 60 交易日超额/夏普跌破阈值触发降仓）；②因子衰减告警（仓库已有 `research_audit/factor_health.py`，每周五自动跑、FAILED/DEGRADED/WATCH 分级）→ **PRD 应把它列为 L8 必备件而非可选**；③实盘 vs 回测信号一致性逐日对账，超阈值告警。

#### P1 级

**N-P1-1 A 股微观结构细节不足，撑不起 §5"真实撮合"验收。** §2 只有一个 `limit_status` 字段，实际至少还需要：①涨跌幅**按板块区分**（主板 10%、创业板/科创板 20%、ST 5%、北交所 30%）——直接决定"能否成交"判定；②2020 起的价格笼子（连续竞价申报价限制）；③T+1 交收（卖出资金当日可用不可取）；④除权除息对持仓成本/可用股数的影响、配股与要约。否则"日频次开盘成交"会在涨跌停/停牌/除权处系统性偏离真实。

**N-P1-2 缺数据字典与单位口径表。** 仓库已有血泪口径：`circ_mv` 单位**万元**（30 亿 = 300000）、`adj_factor` 是**后复权**因子（前复权价 = 原始价 × `adj_factor` / 最新 `adj_factor`）、amount/turnover 单位。§2 列了字段却不定口径，属于"必踩单位坑"的写法。建议 §2 增"字段口径表"并**引用**仓库既有口径，而非重新定义。

**N-P1-3 缺可复现性条款（代码+数据+参数三元组）。** §5 只提"输出净值/成交/持仓"，没提"同一输入必须复现同一输出"。仓库已有 `backtest/hashing.py`，也有真实事故：P10 回测 `risk_state.json` 残留 `nav_peak=12.7` 污染 → 年化虚高至 **35.7%**（真实 18.0%）。建议硬条款：每次回测落盘 `{代码 commit, 数据快照 id/日期范围, 参数全集, 结果哈希}`，且带 state 的入口**必须 run 前强制重置 + 按 run 隔离**。

**N-P1-4 缺过拟合的统计度量。** §9 提了"预注册防 p-hacking"方向正确，但没落到指标。7 策略 + 参数调优 = 典型多重检验场景。建议 §3.4 增 **PBO（过拟合概率）** 与 **Deflated Sharpe Ratio**；§8 Gate 增"参数搜索空间与试错次数必须披露"——否则无法判断 Sharpe 0.8 是真信号还是搜出来的。

**N-P1-5 缺净值与收益口径定义。** 个人投资者自有资金有出入金，需明确 TWR（时间加权）vs MWR；分红再投资 vs 现金；**复利年化 vs 线性年化**。仓库踩过：ATR 卡玛"1.17 → 0.86"正是线性年化虚高口径被修正。§3.4 只列指标名不定口径，必然出现"同一策略两个年化"。

**N-P1-6 缺基准口径表与无风险利率来源。** §9 要求"验收绑五要素含基准"（对），但更基础的是：PRD 通篇没定义"基准"是什么。仓库实测基准口径本就不统一（P01 用中证 500+1000、P10 用沪深 300/等权全 A、ATR 门控用沪深 300）。建议 §3.4 之前先定一张"基准口径表"。

**N-P1-7 缺凭证/数据许可/环境管理。** `config/data_source_keys.json`（Tushare token 等）、Tushare 积分档差异（2000 档无 `ths_daily`/`moneyflow_ind_ths` 权限）、离线包升级制度（`scripts/update_astock_from_e.py`）、备用源 gpsj（`E:/huicexitong/...`，全市场覆盖仅 2015-01 起）。这些是"平台能不能每天跑起来"的前置，应作为**依赖声明**写入 §7。

**N-P1-8 缺文档/参数变更治理。** PRD 自身版本（v1.0 → v1.1）与"**实盘运行中改参数必须重跑 Gate**"未定义。个人项目最容易"边跑边调"，建议明写：参数变更需重新过 §8 全部门槛并留记录。

### 10.3 我对 §9 的 3 处异议（同题不同判断）

**异议 1：S1 的"族归属"判错，会误导排期序。**

### 10.4 排期方法论：建议把"横向分层"改为"纵向切片"（与 §9 最大的不同意见）

§9 给的是**策略优先级序**（S5→S1→S2/S7→S6/S3/S4），但 §1 的 8 层架构 + §7 的 8 项交付物是**横向分层**的：先建完 L1–L8，再上策略。对个人投资者单机项目，这是最大的排期陷阱——L1–L8 全量建完可能耗掉全部预算，却一次真实下单都没验证过；而实盘风险全在 L6/L7（仓库实测：**8 成 bug 在 QMT 集成层，MOCK 测不到**）。

并且 **M0 的成本比 §10 估计的更低——纵向切片在仓库已经存在**：P10 价值小盘V2 / ATR 低波的「数据→评分→build→粘贴→模拟盘→对账→日报」链路已在实盘运行，含 2026-08-14 对账 P0 修复（6+2 账户 position 唯一真相）、pending 300s×3 撤单重报、跌停暂缓队列、4c 账实不符对账协议（T-20260930-001 固化）。**M0 的实际工作不是新建，是规格化**：把这条已在跑的链路按 L1–L8 词汇表反写成文档、补齐缺口，作为平台的 reference implementation；M1 接入 `projects/verification/` 全套件；M2 才按 §9 策略序扩新策略（且每策略先过预注册证伪线）。这样 M0 不引入任何未验证的新代码，排期风险最低。
